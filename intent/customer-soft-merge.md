# 客户合并只能「认人」、不能「执行」—— 研判判了是同一个人,系统里没地方真去合

- **谁提的**:用户(2026-10-14,拍「做执行客户合并,做软合并」「现有硬合并改成软合并」)
- **什么时候**:2026-10-14
- **要解决什么**:研判队列 16 条「客户合并确认」店长认完人就停住,办结永远进不去
  (`ops.回执对照` 里它是 None);现有的硬合并(`server.merge_transit`)撤不回、只搬 3 张表、研判队列不认它。
- **怎么算做完**:总部运营能执行 / 撤销合并且留痕;研判能凭合并记录办结;按客户查的主要入口
  (客户列表 / 详情 / AI 工具 / 开单量体写口)认得关联档;判据 `backend/merge_check.py` 进门禁。
- **明确不做什么**:不搬数据、不相加订单 / 积分 / 会员等级(只关联不累计);不修种子里 B 档汇总列的毛病;
  第 4 批(生命周期 / 归属 / 邀请人)不在本批。
- **状态**:`进行中` —— 2026-10-14 立项,第 1 批在做

## 用户拍的(2026-10-14)

- **做「执行客户合并」,做软合并**(三案里选的;没选硬合并 —— 合错了撤不回来;没选先不做)。
- **现有的硬合并改成软合并**(没选两个都留 —— 同一件事两种结果,员工分不清该用哪个)。
- 前置拍板(10-11 / 10-13):客户合并是两段确认 —— **店长认人 → 总部运营执行**;研判的办结只认总部运营。

## 软合并是什么

- **不搬数据**:B 档案标 `merged_into = A`,B 的订单、量体、积分、评价原地不动。
- **查 A 时把 B 当「关联档案」一起列**,但**不相加** —— 产品文档早写着
  「保留最早客户编号;订单和积分只建立关联、不重复累计」:会员等级按档案存的
  `amount_12m` 判档、积分余额是各自一条链,硬加会算错。
- **B 不再单独出现**:客户列表不列,按 B 查会被引到 A。
- **写到 B 的新东西改记到 A**(开单、量体……),返回里说明「B 已并入 A」。
- **能撤**:撤销后 B 恢复独立,一个字段回到空。
- 谁并入谁:**保留建档最早的那个**(产品文档原规则,硬合并里也是这么写的)。

## 为什么不是硬合并(调查 10-14)

现有 `server.merge_transit` 是硬合并:把 appointment / followup / deposit 三张表改指主档、
拿较新那条覆盖主档的手机号地址、副档 archived=1。三个问题:**撤不回**;**只搬了 3 张表**
(订单、量体 14.5 万行、积分、评价都没动,合完一半在 A 一半挂 B);研判队列不知道它存在。
库里**一次都没执行过**(archived 全 0、op_log 无 MERGE),所以换掉不用清历史。
顺带:它的执行人写死「魏欣新」,和 10-12 修过的销账一样,要改成从登录态取。

## 分批

1. **核心(本批)**:`backend/merge.py`(主档 / 关联档 / 并入 / 撤销,只认总部运营,留痕);
   `merge_transit` 的「已合并」改调它、执行人从登录态取;研判办结认「合并记录」
   (`ops.回执对照` 客户合并确认:None → 合并记录);客户列表隐去已并入的;客户详情列关联档案。
2. **按客户查的 AI 工具**:那 9 处 `id=? OR name=?` 解析到主档;订单 / 着装人 / 评价按关联档一起查。
3. **写入口改记到主档**:order_write / measure_write / rating_write / booking …
4. **其余读路径**(约 75 处,按领域逐批):生命周期、RFM、归属、商机。

## 已知的坑(调查时发现)

- 研判工单里的 16 对(C21000|C21001…)是种子造的,8 对同一人、8 对同名不同人(真值在 truth);
  而**真正同一账户下的重复**是另一批(C10xxx + C21xxx)。两批不是同一批人。
- B 档的汇总列和实际对不上(ordr 里没单、order_cnt 填 1)—— 种子数据的毛病,合并不修它。
- lifecycle_history / cust_owner_log 按档案记,合并后 A 会有两条时间线、两个归属顾问 —— 第 4 批再处理。
- `customer.inviter` 可能指向 B —— 第 4 批。
