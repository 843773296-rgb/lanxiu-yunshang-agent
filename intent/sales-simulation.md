# 模拟销量:让可售天数算得出来,而且谁都看得出这些销量是编的

- **谁提的**:库存预警那条线的会话(2026-09-15 派给假数据工厂这边)
- **什么时候**:2026-09-15
- **要解决什么**:库存预警工具现在对每个 SKU 都说「算不出可售天数」,这么说是对的:
  全库有销量的只有 71 个 SKU,每个只卖过一笔,订单也只跨了 18 天,
  **一个点画不出斜率**。所以缺的是销量数据,工具本身不缺什么。
  但补上的销量是虚构的,**绝不能在任何出口上看起来像真实销售**:
  项目的来源分级(`knowledge/source.py`:public / scale / demo)就是为这个立的,
  demo 声明了自己是虚构的,就不算撒谎。

- **怎么算做完**:
  - `python3 backend/stock_check.py` 最后一行从「**0 行算得出可售天数**」变成一个真实的数
  - `./check.sh` 全绿,尤其是「笔数够了就该算得出来(不是一律不给数)」那条
  - 每一笔模拟订单都能从虚构标记上认出来,标记数 = 模拟订单数
  - 模拟 SKU 的 `stock_log` 按时间串成一条链,链尾就是 `sku.stock`,
    未发货订单的占用加起来就是 `sku.locked`

- **明确不做什么**:
  - **不改 `seed.py`**。库靠「seed.py → run_journey.py 42」再生,
    生成脚本单独放 `tools/simulate_sales.py`,登记进再生步骤
  - **不动库存预警那边的七个文件**(`knowledge/stockalert.py`、`backend/stock_check.py`、
    `backend/api.py`、`prompts.py`、`agent/ops_eval.py`、`agent/ops_eval_judgetest.py`、`check.sh`)。
    「虚构不许像真实」要靠出口去读标记来守,出口是那边的
  - **不碰 `truth` 表和账户凭据列**。前者是评测答案,后者是安全红线
  - **不挪用 `ordr.source` 做虚构标记**。那一列装的是渠道(官网/客服代下单/小程序/门店 Pad),
    一列承载两件事是这个项目撞过五次以上的病
  - **不做定制品订单**。定制品会连带触发分部位选料对账和量体超期检查,
    而可售天数只对标品有意义
  - **不拿夹具客户挂单**。排除规则照 `run_journey.py`:反例夹具 / 客户合并用例 / 评测引用的 / 一号多档
  - **不回写客户汇总字段**(12 个月实付/单数/闲置天数,2026-09-15 已拍板)。
    回写了,虚构销量会顺着会员等级和生命周期流出去,看起来就像真消费

- **状态**:`做完了`(2026-09-15)。四件事已拍板,生成器 `tools/simulate_sales.py` 已提交:
  - 标记:`sim_batch` 表记**来路**(`simulate_sales/v1`),不说「这是虚构的」——
    整个库本来就都是种子数据,那句话会暗示别的是真的
  - 取消单和待付款**留着**,它们是「只数卖掉了的」那条过滤的活体测试数据
  - 客户汇总**不回写**,`--report` 现算出对不上的清单
  - 种子流水**不改**,`--report` 那句话写明「`stock_log` 不是库存的唯一真相来源」
