# 全量门禁该跑在 rebase 的**哪一边**(用户 2026-11-11 让我先查市面做法)

- **谁提的**:我 2026-11-11 午后问用户「推送前要不要每次重跑全量门禁」,
  用户答:「参考市面上最佳实践,比如**两边都好了再跑,只需要跑一次就行了**。
  这只是建议,你先去看看别人是怎么做的。」—— 于是先查,再落。

- **查到什么**:业界这条规矩只有一句,叫 **Not Rocket Science Rule**(Graydon Hoare):
  *自动保证主干永远过全部测试*。bors / GitHub Merge Queue / Google TAP 的落法都是同一个形状:
  **把分支和当时的 main 合起来,对那个合并结果跑一次 CI,过了才 fast-forward main。**
  测的必须就是要落地的那份代码。

- **照这把尺子,我原来的做法有一道缝**:
      ① 在 worktree 上跑全量(397 项,绿)
      ② rebase 到 main
      ③ 推
  **①跑的那棵树和③推上去的那棵树不是同一棵** —— 中间差一次 rebase。
  两边各自都绿、合起来红(语义冲突 / 逻辑冲突)这一类,这个顺序**永远看不见**,
  而且 11-11 第二批推送时主线确实已经被并行会话推进过。
  > **「我验过了」和「我验的是要落地的那一份」,在那个 397 项全绿上长得一模一样。**

- **改成什么**(次数不变,仍是**一次**,只是挪位置):
      ① `git fetch` + rebase 到最新 main
      ② **然后**跑一次全量门禁 —— 跑的就是要落地的那棵树
      ③ 绿了**立刻**推;这期间别人又推了 main,就回 ①(这就是 merge queue 的串行化)
  ⚠️ 对比原来:省掉了「rebase 前那一次」,所以**不比现在更贵**。

- **顺带采纳的一条(batching)**:攒几个提交**一起**过一次门禁,
  而不是一处改一次跑。merge-queue 厂商的说法是能省 50–70% 的 CI 分钟
  (vendor 自己的数,当参考不当依据)。本仓的真实约束不是 CI 分钟,
  是**共享资源锁**:并行会话也在排队,每多跑一轮两边都拖慢。

- **这次没采纳的**:两段式 CI(便宜的每次跑 / 贵的只在入队跑)。
  本仓 `check.sh` 已经是一整轮 397 项、单轮分钟级,拆成两段的收益不够抵
  「两套口径会漂」的代价 —— 而**一条检查在哪一段里跑**漂了之后,
  「它守住了」和「它根本没在这一段跑」长得一模一样(11-11 刚栽过同形状的第七次)。

- **怎么算做完**:下一次推送就按新顺序走,并在汇报里写明门禁跑在 rebase 之后。
- **✅ 已写进 CLAUDE.md**:用户 2026-11-11 拍「现在就写进 CLAUDE.md」(让并行会话也照办),
  落在第 5 节铁律的 `1.5` 条。**随 worktree 一起提交推送** ——
  ⚠️ 主检出那边要 `git pull` 之后才读到这条新规矩。

- **状态**:`做完了`(2026-11-11;两边统一照办)
