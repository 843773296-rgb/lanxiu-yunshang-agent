- **要解决什么**:

  **一句话:旧队列把「AI 出了结论」「有人采纳」「任务升级」「业务办结」
  四件不同的事,统一显示成「已销账」。**

  这不是显示问题 —— 这四件事该触发的下一步动作完全不同,而它们在页面上
  长得一模一样。于是「有人点过按钮」被当成了「这件事办完了」。

  已经复现 / 读到的具体后果(**都有出处,不是推测**):

  | 事实 | 从哪来 |
  |---|---|
  | 已销账但**没有研判记录** 203 条;未研判列表 266 条(其中差评 214) | 2026-10-10 只读接口快照。⚠️ 两类计数有重叠,**不可相加** |
  | **201 条销账全部来自「工单已关闭」,`triage 有结论` 命中 0 条** | `HANDOFF.md` 实测记录。销账的真实依据从来不是研判结论 |
  | 差评错进**客户合并**分支 | 方案会话已复现 |
  | 单条后端失败,**前端显示成功** | 方案会话已复现 |
  | 同步逐条执行,缺整体超时和中途进度 | 代码观察 |
  | 默认候选**没排除已销账** | 代码观察。(但 `ops.queue()` 把已销账标出来并排在最后,不是悄悄混进去 —— 所以改造面比方案预估的小) |

  **为什么现在必须有这份 intent**:这件事此前只写在 `HANDOFF.md` 的一节里,
  `intent/` 里没有,所以它**不在《待办清单.md》上,没有任何人在盯**。
  用户 2026-10-10 问「研判队列什么时候做」时,正确答案是「没有排期,因为没立项」。
  > `intent/README.md` 警告的是「做完了却还挂着」;**反面同样成立 ——
  > 没进 `intent/` 的事不会出现在任何清单上,而「没人在盯」和「排在后面」长得一模一样。**
