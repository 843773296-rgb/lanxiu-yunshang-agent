# 知识库 C:电商运营 —— 标品线「怎么定价、上架、做活动」

- **谁提的**:业务(2026-09-16,「abcd 都做」)
- **什么时候**:2026-09-16

- **要解决什么**:

  这一片是**业务亲自纠正过的那个缺口**。原话:

  > **「虽然我们不做跨境,但是,我们的确是电商平台。」**

  我当时在《技能可挖的业务需求》里把电商运营整片划成了「业务形态不同,不适用」,
  理由是「我们不做跨境」——**从「不做跨境 B2B」滑到「不是电商」,
  中间隔着一整个国内 DTC**。根因是老毛病:**判据贴着表面特征(「跨境」这个词),
  不贴着含义。**

  而这六天做库存预警和多渠道对比时,这个缺口以更具体的形式冒出来了:

  | 撞到的 | 而系统答不出 |
  |---|---|
  | 库存预警排不出「该补多少」 | **补货点** —— 要业务定「缺货一次的代价」 |
  | 「低于 N 件预警」被顶回去了 | 而**正确的线是什么**,没人说得出 |
  | 多渠道对比比不了 | **渠道该怎么运营**,更没有 |
  | 593 个 SKU 一件没卖过 | **压货怎么处理**(清仓?改价?下架?)没有口径 |

- **明确不做什么**:

  - **不替业务定任何一个数。** 补货点、让价幅度、清仓折扣、活动预算 ——
    这些和积分门槛、超时天数是同一类:**编一个数不会报错,只会让人照着它动钱。**
  - **不抄一份通用电商教材进来。** 行业通行做法可以写,
    但**必须标 demo 档并写明「这是行业做法,不是我们的决定」** ——
    「参考」和「我们的规矩」在文档里长得一模一样。
  - **不碰跨境。** 业务明确不做。
- **明确不做什么**(四份知识库共用的四条,`intent/second-knowledge-base.md` 里定的):

  - **不做成一份没被引用的文档。** 现有 12 篇的价值全在「**它被工具读**」——
    相容矩阵接进了 `kb_combo`、判定表接进了 `liability.judge`。
    **答不出「哪个工具会读它」就先别建。**
  - **不用向量检索**,除非这一份真的是**散文形态**。
    「不该用 RAG 的地方用了 RAG」是这一层最常见的错。
  - **不许没有来源等级。** 每条标 public / scale / demo,
    而 `backend/source_check.py` 的欠账上限(39)**只许降不许涨**。
  - **不许和现有 12 篇重叠。** 重叠的两份知识,改一份不改另一份就开始漂,
    **而漂了不报错**。

- **怎么算做完**:

  ① 一份电商运营知识,**每条都标清楚是「行业做法」还是「我们的决定」**
  ② 至少接进一个已有工具:`stock_alert` 的补货点 或 `channel_compare` 的渠道口径
     —— **接不上就说明这份知识没在回答项目的真问题**
  ③ 现在空着的那几个业务决定(补货点、压货处理)在这份文件里**有明确的提问**,
     而不是被一个编出来的默认值填上

- **状态**:`等人的活` —— **行业做法我能写(标 demo),我们的决定必须业务给**。
