# agent 接不上「这是同一件事」——「方案」要成为那个单位

- **谁提的**:业务(2026-09-18,原话「目前 agent 功能太零碎了」)
- **什么时候**:2026-09-18
- **要解决什么**:

  顾问刚问完报价,接着说「那就按这个下单吧」——**agent 不知道「这个」指的是刚才那份报价。**

  根子不是工具少,是**工具按数据切、没按业务动作切**:客户一张表、订单一张表、
  工单一张表,每张表配几个工具。于是 agent 答得出关于**任何一张表**的问题,
  却**没有一个比「一张表」更大的单位**把它们串起来。

  查下来发现:**那个单位其实已经存在,只是 agent 看不见它。**

  | `scheme`(方案)表 | 现状 |
  |---|---|
  | 有自己的生命周期 | ✅ `草稿 → 已保存 → 已锁定 → 已失效` |
  | 挂客户但不等于客户 | ✅ 有 `customer_id`,且**库里已有客户并行多条** |
  | 承载一次具体诉求 | ✅ 形制 / 面料 / 工艺 / 颜色 / 配饰 / 版型全在上面 |
  | **agent 够得着吗** | ❌ **59 个 MCP 工具里,关于方案的是 0 个** |
  | **订单指得回来吗** | ❌ `ordr` 没有 `scheme_id` |

  **所以这不是要造一个新概念,是把一个已存在的概念接进 agent 的世界。**

- **怎么算做完**:

  1. `get_scheme` 上线(**资源型工具**,和 `get_order` 一个形状:按 `scheme_id` /
     `customer_id` / `status` 取),进 `SHOP_SCHEMAS`
  2. `ordr` 加 `scheme_id`,下单时回填;`backend/scheme_check.py` 增加一条
     「转过单的方案必须指得回订单,反之亦然」
  3. 报价结果**结构化落到方案上**,不再只是一段话
  4. Hook 每轮注入「当前方案」——放进 `make_hooks(state)` 那个跨 hook 的 `state`
  5. **判分器先写**:构造「指代推进」对照用例(报价后用「这个 / 刚才那套」推进),
     判**取到的 `scheme_id` 对不对**;判分器绿了才跑模型
  6. **咬合**:把 Hook 注入那一行去掉,确认对照用例变红

  门禁里盯着它的:`backend/scheme_check.py`(已在 check.sh 第 53 步)、
  `backend/page_smoke_check.py`(方案相关页面真跑得起来)。

- **明确不做什么**:

  - **不新开动词工具。** 不要 `lock_scheme` / `convert_to_order` 这种 —— 业务方 2026-09-18
    定的规矩:**MCP 跟表走、跟 API 走,场景该由 Skill 编排,不该由 MCP 增生**。
    状态流转只是 `scheme.status` 的值变化,走**已有的写接口**(`check_write` 预演 + 写工具白名单)。
  - **不把方案号塞进对话文本让模型记住。** 理由见下面第 ④ 问 —— 压缩是有损的,而且丢了不报错。
  - **不做会话转移。** 会话归属是绑死到人的(「别人的会话一律拒」)。
    **方案能转手,会话不能** —— 这两件事必须分开,混在一起会把「换人接手」做成越权。
  - **「同一时刻只有一条方案能处于已锁定」这条约束不做 —— 业务 2026-09-18 明确否掉了。**
    我提过这条,业务的回答是「**可以多条同时锁**」。对婚庆类这是对的:
    婚服、敬酒服、伴娘服本来就各锁各的。

    ⚠️ **这个回答有个直接后果,比约束本身更要紧:「锁定那条」不再是一个能消歧的说法。**
    我原来假定锁定唯一,于是顺理成章会想「指代不明时就取已锁定那条」——
    而业务一否掉,这条捷径就不成立了。**指代消歧只能靠方案号,不能靠状态。**
    这也是为什么这个问题必须先问:它不只是要不要加一道校验,
    它决定了 agent 遇到「就按那个下单」时**有没有兜底可走**(答案是没有)。
  - **不动那 7 个已有的场景型工具**(`can_order` `recovery_queue` `stock_alert` 等)。
    它们现在工作正常,删了要动评测、动提示词、动 skill,收益是零 ——
    **改一个能跑的东西只为了让它更符合分类,是拿风险换整齐。** 新规矩只对新增生效。

- **五问**(业务方 2026-09-18 定的:每个功能点立项时必须一起回答):

  **① 指标是哪几个、怎么设计的**

  主指标:**跨卡点接续成功率** —— 顾问说「就按刚才那个下单」时,agent 取到
  **正确 `scheme_id`** 的比例。设计上最要紧的一点:**这个指标可机器判定** ——
  判的是取到的号对不对,**不是「回答得好不好」**。对照组是现在(没有方案对象),预期接近 0。
  副指标:方案→订单转化率、方案平均存活天数、同一客户并行方案数。

  **② Agent Loop 在哪一环体现**

  现在的 loop 是**无状态问答**:每一轮模型自己从对话里猜「在说哪件事」。
  方案对象进来之后,loop 多了一个**状态载体** —— 每轮开头由 Hook 注入当前方案。
  **这就是 loop 从无状态问答变成有状态推进的那一处。**

  **③ Harness 提供了什么,我们提供了什么**

  Harness(`agentsite/sdk.py`)管循环、上下文、工具调度,**我们只提供环境**。
  而 `make_hooks(state)` 里那个跨 hook 共享的 `state` dict,
  **就是 harness 留给我们挂状态的口子** —— 方案号放在那里,不放在对话里。

  **④ 模型已经会自动压缩上下文了,为什么还要自己管**

  > **自动压缩压的是「读起来连贯」,不是「标识不丢」。**
  > 压缩是有损的,而且**丢了不报错**。压完之后模型很可能仍然记得
  > 「在聊一套唐制襦裙」,却**丢掉了 SC2601 这个号** ——
  > 而这两种状态在对话里长得一模一样,直到它**按错误的方案下了单**。
  >
  > 分工:**叙述交给模型压,标识必须由我们显式携带。**

  **⑤ 怎么证明它是对的**

  判分器先写 → 绿了才跑模型 → **咬合**(去掉 Hook 注入,确认变红)。
  不红就说明这套指标根本没测到它 —— 而**没测到和测过了在成绩单上长得一样**。

- **状态**:`进行中`(2026-09-18 立项)—— 做完它,需求池里 D1(报价转订单)、
  D3(校验不通过顺手补)、D5(跨卡点接续)**三条会同时解掉**,因为它们缺的是同一根线。
  ⚠️ 开工前要业务确认一件事:**「同时只能锁一条方案」这条约束成不成立。**
