# 把 `*.advisor` 那七列真正删掉

- **谁提的**:我(做「主数据被引用了没有」那一轮时列出来的)
- **要解决什么**:那七列存的是**顾问的名字**,而名字是别处的事实的副本。
  现在工号是引用、名字是**有检查盯着的缓存** —— 缓存和真相长得一样,
  而漂了不报错。
- **怎么算做完**:`backend/advisor_ref_check.py` 从 check.sh 里**撤掉**
  (它是为这次迁移临时顶着的),同时页面改成 join staff 取名字。

  门禁里盯着它的两条:`backend/advisor_name_check.py`(页面上那一栏有没有名字、
  对不对得上)、`backend/advisor_write_check.py`(写了名字列的 INSERT
  有没有一起写工号)。
- **明确不做什么**:**不在页面改完之前删列** —— 删了页面会静默显示空名字。
- **状态**:`进行中` —— **读的一侧和写的一侧都改完了,只差最后一步「删列」,
  而删列被一件更大的事挡着**(2026-09-16)。

  ### ⚠️ 先纠正一个数:不是 38 个页面,是 **7 个**

  「38」是**页面总数**,不是受影响的页数。实测只有 7 个页面函数会吐出顾问名字。

  > **一个错的数字能把一件半天的事压在待办里好几天。**

  ### 做完的

  | | |
  |---|---|
  | 读的一侧 | 7 个页面统一走 `server.填顾问名()` —— **拿工号去员工表取**,不读那一列 |
  | 筛选下拉 | 客户列表的「顾问」筛选也改成从员工表来(原来直接读那一列) |
  | 业绩统计 | `guide_perf` 从 `WHERE advisor LIKE '%林岚%'` 改成按工号 |
  | 写的一侧 | **21 条写顾问名字的 INSERT,每条都带上了工号** |
  | schema | 10 个工号列写进了 `seed.py` 的建表语句 |
  | 网 | 两道新检查(见上) |

  **验证方式不是「看起来对」**:把 11 张表的名字列**全抹空**,
  页面照样认得出人(77 处一处不少)。

  ⚠️ 第一次抹空时 77 掉到 68 —— 差的 9 处是客户列表的顾问筛选下拉,
  它还在直接读那一列。**删了列下拉会变空,而页面照常打开** ——
  这正是这条 intent 自己警告的那种失败方式,而没有那次实验是看不见的。

  ### ⚠️ 顺带挖出来的、比这条待办要紧得多的事

  **这次迁移原来只做了一半**:引用建好了(回填 5848 行),
  **而写的一侧还在只写名字** —— 三处 INSERT 从不写工号。

  而 `advisor_ref_check` 查的是**已有的行**,门禁跑的是静态种子数据,
  **那几条写路径根本没被走过** —— 所以它一直绿着。

  > **「数据是对的」和「产生数据的路径是对的」是两件事。**
  > 前者今天成立,后者明天就把它推翻,而中间不会有任何提示。

  根因是 **schema 的真相分裂成两处**:工号列不在 `seed.py` 的建表语句里,
  是 `fix_advisor_ref.py` 事后 `ALTER` 加的 —— 在 seed 的世界里那一列压根不存在。

- **状态**:`做完了`(2026-09-16 晚)—— **11 张表的名字列全部删除,从零重建通过**。

  ### 删掉之后真正消失的东西(这才是收益)

  | 消失的 | 它原来为什么存在 |
  |---|---|
  | **`booking.staff_of_advisor` 那座「桥」** | 档案存名字、员工表存工号,只能**按名字连**;要容忍三种写法、还要处理**同名** |
  | **`substr(c.advisor,1,3)`** | 靠**截字符串前三位**连人 |
  | **`_量体人名(c, no)`** | 写量体记录前**先把工号翻成名字** |
  | **seed 里一整段「按名字对工号」的迁移** | 历史日程只有名字 |
  | ⚠️ **`advisor=?` 配 `me["name"]` 的权限隔离** | **两个同名顾问会看到彼此的订单** —— 那是越权,不是显示问题 |

  最后一行是最实在的一项:**这个风险现在结构性消失了**,不是靠谁记得。
