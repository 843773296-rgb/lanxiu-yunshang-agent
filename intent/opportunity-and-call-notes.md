# 顾问在电话和上门沟通里察觉到的商机,现在全丢在脑子里

- **谁提的**:业务(产品负责人)
- **什么时候**:2026-09-20
- **状态**:`进行中`

---

- **要解决什么**

**客户不是一通电话就成单的,而中间那几次沟通,系统一个字都没留下。**

现在这条链是断的:

    引流/促活 → 顾问打电话 → 客户预约到店/电话沟通 → ？？？ → 方案 → 订单
                                                    ↑
                                              这一段是空的

具体空在三处:

**① 沟通内容没有承载。** `followup` 表有 24 条记录,而客户有 965 个 ——
**平均每 40 个客户才有一条跟进**。而且 `content` 字段是一段自由文本
(「客户确认到店时间」),里面没有「客户说了什么」「有什么异议」「下一步是什么」。

**② 商机只是一个贴在客户身上的静态标签。** `tag` 表里有「高意向」42 个、
「观望中」18 个、「价格敏感」4 个 —— 它答不了:

    这个商机值多少钱? 推进到哪一步了? 下次什么时候该再跟? 上次为什么没成?

而顾问脑子里那个「李太太她姐姐十月结婚,可能要做伴娘服」**就是一个商机**,
它现在只存在于顾问的记忆里。顾问离职、请假、转岗,它就没了。

**③ 「打过去说什么」没有依据。** 系统**算得出**先打给谁
(`get_member` 的八档生命周期 + 档内 RFM 排序),但**算不出打过去说什么** ——
而后者才是顾问真正卡住的地方。

## 链条上的位置(业务 2026-09-20 定)

    商机 ──触发──> 方案草稿 ──> 方案锁定 ──> 订单
     ↑                ↑
     │                └─ 客户在消费端**选中的洽谈服饰**,
     │                   或跟导购**沟通内容里的服饰**
     │
     └─ 「这个客户可能要买东西」的一次判断。**可以完全没有服饰信息。**

**商机不是草稿状态的方案** —— 业务明确否掉了这个等同。
**商机是方案的前置触发之一**(还有别的触发,比如客户在消费端自己选)。

> **这条边界可机器判定,要做成检查:**
> 商机**可以**没有任何服饰字段;方案草稿**必须**至少挂一件具体服饰。
> 两者混同的后果是:同一件事在两个对象里各记一份,
> **而两份不一致时没人知道哪个是真的**。

## 商机的第二个来源:**说过但没满足的诉求,等到供给变了才成立**(业务 2026-09-20 补)

客户在某通电话里说「我想要红色的」,最后**没买成**,或者**买了蓝色**。
今天上新了红色款 —— **这也是商机,而且必须识别出来。**

这个来源和「这次沟通里新发现的」是**两套机制**:

    ① 这次沟通里发现的     逐字稿 → 现在就有一个商机
    ② 历史诉求 × 供给变化   逐字稿 → 记下「想要红色」→ 搁着
                           → 上新/到货/降价/活动 → **回头把它捞出来**

### 要紧的一条:**「她拒绝了」和「当时没货」,在「没成交」这个表示上一模一样**

但它们该触发的动作**完全相反**:

| 没成交的真实原因 | 该怎么办 |
|---|---|
| 她看了不喜欢、嫌贵、不需要 | **永久关掉**。上新了也别再去烦她 |
| **当时没有红色** / 工期赶不上 / 尺码断了 | **搁置等供给**。上新红色那天要唤醒 |

**混成一个「已丢单」,两种都会错**:要么上新了不去找她(漏商机),
要么她明确拒绝过还一再去推(骚扰客户)。

→ 所以商机的终态**不是一个**,至少是两个:`已关闭(不再唤醒)` 和 `搁置(等供给)`。
**搁置必须写清等的是什么**(等红色 / 等某个形制 / 等价格),否则唤醒时匹配不上。

### 「买了蓝色」算不算满足了「想要红色」——**这条要业务定**

两种读法都讲得通:

- **算**:她要的是「一件衣服」,颜色是次要的,买了就是满足了
- **不算**:她要的就是红色,蓝色是将就,红色上新了还该告诉她

**不替业务猜。** 猜错的两个方向都有代价:
判「算」会漏掉真实商机;判「不算」会把已经买过的客户再推一遍。

### 这个来源对数据结构的硬要求:**诉求必须是结构化的,不能是一段话**

「客户想要红色的」写成一段自由文本,**上新的时候没法拿它去匹配**。
必须落成可比对的字段(颜色 / 形制 / 面料 / 场合 / 预算 / 尺码),
**并且每一条都要指得回逐字稿里的原话**。

> 指得回原话是硬要求,不是锦上添花。
> 顾问隔三个月被系统提醒「去找李太太推红色」,他第一句会问「凭什么」——
> 答得上来的是那句原话(「2026-06-12 那通电话,她说『要是有正红的我就定了』」),
> **答不上来的话,这条提醒和瞎猜没区别,而顾问只要被瞎猜坑过一次就再也不看了。**

### ⚠️ 这个来源最容易做成骚扰

回捞是**一对多**的:一次上新可能唤醒几百条搁置诉求。要有闸:

- **时效**:三年前随口说过一句,今天还要不要捞?**业务定一个期限。**
- **匹配得有多准才算数**:「想要红色」对上「酒红」算不算?
- **同一个客户多久之内不重复推**
- **仍然不给成单概率** —— 和 `get_member_priority` 那条一样:
  **给判断依据,不给数字**。一给概率顾问就会拿它当承诺。

- **怎么算做完**

1. **商机对象上线**,有生命周期、来源、预估、下一步、丢单原因;
   `backend/opportunity_check.py` 进 `check.sh`,至少盯住:
   - 商机→方案的触发关系指得回去,反之亦然(**和 `scheme_check` 里
     「转过单的方案必须指得回订单」同一个形状**)
   - **商机可以没有服饰信息,方案草稿不可以** —— 这条边界真的被守着
   - 样本量下限:商机数少于 N 时这些检查**报「没扫到东西」,不报通过**

2. **录音转文本**接进来,一次沟通一份逐字稿,挂在商机上。
   ⚠️ **转写不是 Claude 能做的事** —— 实测本机没有任何语音识别
   (`whisper` / `faster_whisper` / `funasr` / `vosk` / `ffmpeg` 全都没有),
   而 `agentsite/sdk.py` 只有图片通道,**模型不收音频**。
   这是一个**外部依赖**,见下面「等人拍板」。

3. **技能:从逐字稿出「任务总结 + 商机研判 + 下一步指引」。**
   为什么是技能不是工具 —— 按项目一贯的判据(**中间结果要不要经过模型**):
   读到「客户说预算两万但想要云锦」之后,**下一步该查什么取决于读到了什么**
   (查云锦这个预算够不够?还是查有没有替代料?还是查她上次为什么没成?)。
   这个循环没法提前枚举成一次调用。

4. **判分器先写,绿了才跑模型。** 判「从这段逐字稿里,该不该识别出商机」
   「下一步指引指的那件事,是不是真的在库里」——
   **判的是可机器判定的东西,不是「总结得好不好」**。

5. **咬合**:把「商机必须指得回触发它的那次沟通」那条检查改坏,对照用例要变红。

6. **「已关闭」和「搁置等供给」在库里分得开**,而且有检查盯着:
   搁置的必须写清**等的是什么**(可匹配的字段,不是一段话);
   已关闭的**不许被上新唤醒**。
   ⚠️ 这条要有咬合:把两种终态合并成一个「已丢单」,对照用例必须变红。

7. **每条结构化诉求指得回逐字稿里的原话**(位置或原句),
   检查:**指不回原话的诉求不许进回捞池** —— 那种提醒和瞎猜没区别。

- **明确不做什么**

- **不做实时通话分析。** 通话中给顾问弹提示是另一件事(要低延迟、要流式、
  要和电话系统对接),和「事后出总结和指引」完全不是一个工程。
  混在一起做,会让本来能做成的那半也做不完。

- **不替顾问下结论说「这单能成」。** 输出的是**依据和下一步**,不是成单概率。
  理由和 `get_member_priority` 那条一样:**RFM 是排序不是预测**,
  一给概率,顾问就会拿它当承诺。**商机研判同理 —— 给判断依据,不给数字。**

- **不做会话/商机转手。** 商机能换负责人(顾问离职要交接),
  但**这是一次有记录的移交,不是悄悄换个字段** ——
  和「方案能转手、会话不能」同一条理由:悄悄换掉负责人,
  会让原来那个人的列表凭空少一行,而他不会去问,他会以为自己记错了。

- **不做「自动给客户发消息」。** 回捞出来的商机是**给顾问的提醒**,
  由人决定要不要联系、怎么联系。自动推送踩的是完全另一类风险,
  而且一旦推错,**收不回来**。

- **不新开动词工具**(`create_opportunity` / `close_opportunity` 这种)。
  沿用 2026-09-18 定的规矩:**MCP 跟表走、跟 API 走,场景该由 Skill 编排**。

- **营销/客服不看逐字稿原文** —— 见下面「等人拍板」第 3 条,**这条待确认**。

## 等人拍板的(不替业务猜)

**① 转写放哪儿跑。**

| | 代价 |
|---|---|
| **本机转写**(装 whisper 一类) | 音频不出系统;要装、要占资源、准确率要自己验 |
| **云服务转写** | 装起来快;但**客户通话音频会离开我们的系统**到第三方 |

业务已定「录音同意写进应用说明、不二次确认」——
**但那份说明里写的是「我们录音」,不是「我们把录音交给第三方」。**
选云服务的话,应用说明里得再加一句,否则**说明书和实际做的事不一致**。

**② 录音同意要不要能撤回。**

业务已定:电话/上门**默认同意录音**,写进应用说明,不二次确认。**按此执行。**

但有一条工程上的事要一起定:**撤回走不走得通。**
`consent` 表现在管两档(身体数据 845 条、未成年人 191 条),
**两档加起来撤回过 0 条** —— 也就是说那条分支**从来没被走过**。
录音这一档要是也没人走,那又是一个**假开关**:
界面上写着「可撤回」,而代码路径从没跑通过。

→ 建议:录音同意作为 `consent` 的第三档,**并且这一档的撤回必须有一条咬合
盯着**(在库的副本上真撤一条,验它真的生效)。

**③ 营销人员和客服,看到什么粒度?**

业务已定:面向**顾问、店长、营销人员(含客服)**,都给下一步指引。

但「给指引」和「看逐字稿原文」是两件事,得分开定:

| 角色 | 建议粒度 | 理由 |
|---|---|---|
| 顾问 | **自己的全文** | 是他自己打的电话 |
| 店长 | **本店全文** | 和现在任务隔离的口径一致(店长看本店) |
| 营销 / 客服 | **聚合与结论**,不看逐字稿 | 「这批客户里 12 个提到价格敏感」够用了;
给全量逐字稿是一个比现在宽得多的口子 |

**这只是建议。** 如果业务要营销也能看全文,那也行 ——
但要**明说**,因为它会改变现在「顾问之间隔离在查询层」那条硬规矩的边界。

## 五问(需求池 §5 要求,立项时一起答)

1. **指标**:主指标 **商机识别召回率** —— 人工标注的逐字稿里有商机的,
   agent 识别出来的比例。**可机器判定**(对照人工标注),不是「总结得好不好」。
   副指标:商机→方案转化率、商机平均存活天数、顾问采纳下一步指引的比例。
2. **Agent Loop 哪体现**:读逐字稿 → 发现「预算两万 + 想要云锦」→
   **自己决定去查云锦在这个预算下做不做得出来** → 再决定下一步指引写什么。
   **下一步查什么取决于上一步读到什么**,这是 loop,不是一次调用。
3. **Harness 提供什么**:技能的 progressive disclosure(逐字稿可能很长,
   不能整份塞进上下文)、跨 hook 的 `state`(当前在谈哪个商机,
   和「当前方案」同一个机制)。
4. **为什么不靠模型自动压缩**:一通电话的逐字稿几千字,
   压缩保的是「读起来连贯」,**不保「客户说的那句『不要撞色』还在」** ——
   而那句话没有编号,却决定下一步做什么。
5. **怎么证明它是对的**:判分器先写(见「怎么算做完」第 4 条),
   再跑模型,而且要咬合过。
