# 「库是可再生的」这句话是假的 —— 从零重建,门禁红 26 项

- **谁提的**:我(2026-09-16,做 advisor 删列时为了验证 seed 改动而重建了一次库)
- **什么时候**:2026-09-16

- **要解决什么**:

  `HANDOFF.md` 第 34 行写着:

  > ⚠️ **库是可再生的**:`python3 backend/seed.py` 一把生成,
  > 再 `python3 tools/run_journey.py 42` 造完整旅程。
  > 最后 `python3 tools/simulate_sales.py` 补 6 个月标品销量。
  > **别去抢救某个特定的库文件。**

  **实测:照这三步从零重建,`./check.sh` 红 26 项。**

  ### ⚠️ 这是这个项目最危险的一种状态

  库能一直是绿的,**只因为没有人从零重建过它**。它是一路 `ALTER`、
  一路跑 `fix_*.py` 补出来的,而那些步骤**不在文档里、不在门禁里、
  不在任何清单里**。

  > **一个「能跑」的库和一个「重建得出来」的库长得一模一样** ——
  > 直到有人换台机器、或者需要回到某个干净状态。

  而交接文档那句「别去抢救某个特定的库文件」**会让人真的把它删掉**。

  ### 查出来的具体缺口

  | 缺口 | 表现 |
  |---|---|
  | **`fix_product_pattern.py` 是坏的** | `NameError: name '拍板分档' is not defined` —— 跑不起来 |
  | **三个 `fix_*.py` 不在流程里** | `fix_advisor_ref` / `fix_order_measure` / `fix_product_pattern` |
  | 定制部件金额没有明细 | 重建后「有定制部件金额的订单行必须有明细」红 |
  | 订单行缺下单时的版型版本 | 重建后缺 28 条 |

  ### 2026-09-16 下午已经补掉的(门禁红项 13 → 12,而露出的洞比补掉的多)

  ⚠️ **补一个洞会露出下一个** —— 旧洞挡着新洞,这是重建这类活的常态:

  | 补掉的 | 而它挡着的下一个 |
  |---|---|
  | `run_journey` 建的定制单**没有部位明细**(钱收了,选了什么一个字没存) | → 露出「外层部位有面料就得有工艺」 |
  | 同上,**没记下单时的版型版本**(29 条) | — |
  | `run_journey` **拿标品下定制单**(31 单里 24 单) | ← 是上面那条的**根因**:标品没有部位选项,明细拆不出来 |
  | 渠道名**一个空格**(`门店Pad` vs `门店 Pad`) | → 露出 `sys_code` 和真实数据**是两套东西** |

  最后一条最值得记:**那个空格不是随手打的,是照着 `sys_code` 抄的**——

      sys_code 说:微信小程序 / **门店Pad** / 门店A / 门店B
      ordr 实际是:微信小程序 / **门店 Pad** / 官网 / 客服代下单

  **四个里只有一个对得上。** 枚举表有两个数据里不存在的,数据有两个枚举表没有的。
  > **两个来源都在,而写代码的人照哪一个都像是对的。**

  已加 `backend/syscode_check.py` 钉住(对不上 6 条,只许降不许涨),
  归零要业务确认「门店A / 门店B」是历史遗留还是将来要用的。

  ### 已经顺手补掉的一块

  **工号列根本不在 `seed.py` 的建表语句里**,是 `fix_advisor_ref.py` 事后
  `ALTER TABLE ADD COLUMN` 加的 —— **schema 的真相分裂成两处**。
  2026-09-16 已把 10 个工号列写进建表语句,`seed` 现在自己就产出完整工号。

  归因数据:**用原版 `seed.py` 重建红 26 项,用改过的红 8 项。**
  (所以「重建会坏」是本来就有的,而且比现在严重三倍多。)

- **明确不做什么**:

  - **不把 `fix_*.py` 简单塞进 HANDOFF 的步骤里就算完。**
    它们是**一次性迁移脚本**,名字里的 `fix` 说明它们修的是历史遗留 ——
    把一次性脚本变成常驻流程的一环,等于承认 seed 生不出正确的数据。
    **该修的是 seed,不是流程的长度。**
  - **不为了让重建变绿去放宽检查。** 那 26 项红的每一条都在说一件真事。
  - **不删 `backend/lanxiu.db`。** 在重建真的可用之前,那个文件**是不可再生的**,
    而 HANDOFF 现在正在告诉人它可以被删。⚠️ **这一条最急。**

- **怎么算做完**:

  ① 一条命令(比如 `tools/rebuild.sh`)从零重建,`./check.sh` **全绿**
  ② `HANDOFF.md` 里那段再生步骤和它**完全一致**,
     并且有检查盯着「文档写的步骤和脚本里的步骤一样」
  ③ `fix_product_pattern.py` 要么修好,要么明确废弃(**「坏着的」和「不用的」
     在目录里长得一模一样**)

  门禁里盯着它的三条:`tools/intent_check.py`(重建脚本在不在、文档指不指向它)、
  `backend/advisor_write_check.py`(写入侧)、`backend/syscode_check.py`(字典表)。

- **状态**:`做完了`(2026-09-16 下午)—— **从零重建,`./check.sh` 全绿**。

  红项清理轨迹:**26 → 13 → 12 → 9 → 7 → 0**
  (26 是原版 seed;13 是补上工号列之后;后面几档见上面那张表)

  ⚠️ **7 → 0 那一段不是修数据,是修我自己的测法**:副本里没软链 `.venv`,
  于是 7 项「失败」全是 `No such file or directory` ——
  **而它们和数据问题混在同一份报告里**。
  软链过去之后是 0。**一个环境问题和一个数据问题,在失败列表里长得一模一样。**

  ### 交付的东西

  | | |
  |---|---|
  | `tools/rebuild.sh` | **一条命令**从零重建,顺序写在脚本里 |
  | `HANDOFF.md` | 改成**指向那个脚本**,不再手抄步骤 |
  | `tools/intent_check.py` | 两条新检查:脚本在不在、文档指不指向它 |

  **为什么不是「把步骤补全再抄进文档」**:抄的那份照样会漂 ——
  而**漂了的重建步骤比没有步骤更糟**:人照着跑,以为重建成功了。
