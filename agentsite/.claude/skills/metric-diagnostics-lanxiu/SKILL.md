# 指标异动诊断

> **改造自第三方 `metric-diagnostics`**(第三方技能包里提取的,原文英文)。改了什么:
> ① 原文让模型自己去翻数据源、写查询核对口径 —— 本系统 agent 碰不到库,**改成只调本系统 MCP 工具**,口径以工具返回里写明的为准;
> ② 删掉原文后半「KPI 周报 / 记分卡」那一整段 —— 门店经营报告已有自己的技能和取数包,不在这里再写一套;
> ③ 原文没有业务阈值,这里也**不加任何「变化超过几成算异常」的门槛**;
> ④ 补上本系统特有的坑:营收按付款日 / 退款日归周、两把销量尺不一样、渠道和活动一一对应拆不开、演示数据里种下的规律。
> 状态默认「已安装待审查」,要总部运营在 Skill 管理页审查后放进试运行才会被执行闸放行。

## 什么时候用

有人问**一个数的变化或差异是怎么来的**:

- 「上周营收为什么比前一周少了一截?」
- 「九月卖得没八月好,差在哪?」
- 「这个月预约到店的转化怎么变差了?」
- 「静安店的评价分比上个月低,是哪里出了问题?」

## 什么时候不用

- **只问一个数是多少**(「上周营收多少」「九月卖得最好的是什么」)—— 直接调 `weekly_revenue` / `sales_rank`,不走这个技能
- **要一整份日报 / 周报 / 月报** —— 那是经营报告的流程(`store_report` 取数包),不在这里拼报告
- **问某一个客户、某一单** —— 用客户 / 订单工具
- **问「该怎么调预算 / 要不要关掉某个活动」** —— 那是决定,不是诊断;这里只给原因和建议看什么,不替人拍板

## 用哪些工具(只调这些,全是只读)

| 要诊断的数 | 取数工具 | 能拆的维度 |
|---|---|---|
| 营收 | `weekly_revenue`(week 或 start+end) | 实收 / 退款 两项 |
| 销量、卖了什么 | `sales_rank`(month 或 start+end,by=商品 / SKU / 品类) | 商品、SKU、品类;件数 / 金额两种排法 |
| 下单量 | `orders_by_date`(month 或 start+end,field=下单) | 逐单列表 |
| 预约到店转化 | `appt_funnel`(since / until) | 约 → 确认 → 到店 → 量体 → 下单 各环节 + 四种流失 |
| 成交率 | `conversion_rate` | 按接待人 / 按归因 —— **两个数回答不同的问题** |
| 评价 | `rating_overview`(days) | 按门店、按月 |
| 版师视角的受欢迎 | `product_ranking`(month) | 形制 / 面料 / 工艺 |

## 第一步:把问题说清楚

写下四样,缺哪样就问哪样,**不替人猜**:

1. **哪个数**,按哪个工具的口径(「营收」= 实收减退款,按付款日归周 —— 不是下单金额)
2. **哪一期和哪一期比**(上周 vs 前一周、九月 vs 八月)—— 比较期必须是**同样长、同样口径**的两段
3. **范围**:哪家店 / 全部(工具按登录身份定范围,店长只看得到本店)
4. **问的是哪一种**:是「变了多少、为什么」,还是「两个地方的数对不上」

## 第二步:先复现,再找原因

两期都调一遍工具,把**两期的数和差多少(绝对值、百分比)**写出来。
**数复现不出来就不找原因** —— 用户说「掉了一半」而工具算出来只差 8%,先把这个差说出来,问他看的是哪个数。

## 第三步:确认两期能比

逐条看工具返回里的「口径」「⚠️」「不算在内」:

- **这一期过完了吗**:返回里有「这一周还没过完」就是半期对整期,**不能比**,照实说
- **两把尺是不是同一把**:`sales_rank` 不算待付款、`product_ranking` 算;两边件数不一样而两个都对
- **退款日是近似的**:个别退款可能被归到相邻一周 —— 差额很小的时候要提一句
- **样本量**:每个比率后面都跟着条数,几条算出来的变化不当成结论

## 第四步:拆驱动

挑**最少的几刀**,能解释大部分变化就停:

- **加总型的数**(营收、销量)→ 按门店 / 品类 / 商品拆,算每一块对总变化贡献了多少
- **比率型的数**(转化率、差评占比)→ **分子和分母分开看**:是到店的人少了,还是到店后下单的少了
- **区分结构变化和组内变化**:总数掉了,可能是贵的品类卖少了(结构),也可能是同一个品类里卖少了(组内)—— 两种该做的事完全不同
- 营收:先拆成**实收**和**退款**两项,再往下拆

## 第五步:给结论

按这个顺序写:

1. **一句话答案**:变了多少,主要是哪一块
2. **已证实**:数字直接撑得住的(「静安店少了 4.2 万,占总降幅的八成」)
3. **可能**:时间对得上但没有直接证据的(「那周恰好没有活动」)—— 明写是推测
4. **查不清**:工具取不到、或者数据本身说不清的
5. **建议接着看什么**(只是建议,不是已安排的事)

## 硬规矩

1. **数字只照工具返回说**,不心算新数、不拿两个工具的数相加相减拼一个没人算过的指标
2. **不拿相关当原因**。「这周有活动、这周营收高」不等于「活动带来了营收」—— 时间对得上只能写进「可能」
3. **不许加门槛**。「下降超过 20% 算异常」这种线本系统没有拍过,不许自己划
4. **渠道和活动拆不开**:`channel_compare` 写明了渠道和活动一一对应、样本小,**不许拿渠道当原因**
5. **演示数据里种下的规律要说出来**:`product_ranking` 返回里「撞在种下的规律上」那一条,诊断里照实带上
6. 两个成交率(按接待人 / 按归因)**不许混着比**,说清用的是哪一个

## 出错了怎么办

- **工具报错 / 没登录** → 照实说取不到,不编数;没权限(比如顾问问全店评价)就说清这个数要店长或总部看
- **比较期还没过完** → 说「这一期截到今天,还不能和整期比」,问他要不要换成上一个完整期
- **两期口径对不上**(一个按付款日、一个按下单日)→ 停下来说明,不硬比
- **拆完解释不了大部分变化** → 结论写「主要原因查不清」,列出已排除的几刀;**不为了凑一个原因去挑一个碰巧对得上的**
- **数据太少**(几条评价、一两单)→ 说「样本太小,看不出原因」,这本身就是结论

## 例子(示例)

问:「上周营收为什么比前一周少?」(下面的数字只是示意格式,**真答时一律照工具返回**)

1. `weekly_revenue()`(上周)和 `weekly_revenue(week=前一周任意一天)` → 上周 18.6 万、前一周 23.1 万,少 4.5 万(−19%)
2. 拆实收 / 退款 → 实收只少 1.2 万,**退款多了 3.3 万** —— 主要是退款,不是卖少了
3. 退款日是近似的 → 提一句可能有个别退款跨周
4. 结论:「已证实:少的 4.5 万里有 3.3 万是退款变多;可能:……;建议接着看:上周退款集中在哪几单(`get_refund_trace`)」
