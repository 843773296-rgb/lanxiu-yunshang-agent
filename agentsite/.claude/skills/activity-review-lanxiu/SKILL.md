# 活动投入产出复盘

> **改造自第三方 `marketing-roas-analyzer`**(第三方技能包里提取的,原文面向海外独立站的 Meta / Google / TikTok 广告投放)。改了什么:
> ① 数据来源从 GA4、广告后台**改成只调本系统 `activity_roi` / `channel_compare`**;
> ② **删掉原文全部业务门槛**:保本 ROAS 公式和「低于保本就砍」、各渠道「目标 ROAS 倍数」、预算 ±20% 的加减规则、
>    花费进度 110% / 90% 线、频次 > 2、「平台之间默认重复 20–30%」—— 这些门店都没拍过板,不许引入;
> ③ 保留它和平台无关的三条方法:**成本和成交都有好几种口径要并列**、**归因期外的成交不能算进来**、**系统自报的数不当真**;
> ④ 补上本系统的事实:活动表上的「报名 / 成交」两列是随机数;渠道和活动一一对应,两者分不开。
> 状态默认「已安装待审查」,要总部运营在 Skill 管理页审查后放进试运行才会被执行闸放行。

## 什么时候用

要评一个或几个**营销活动划不划算**时:

- 「七夕那个活动做得值不值?」
- 「今年这几个活动哪个效果最好?」
- 「活动投进去的钱回来了没有?」
- 「下次活动的钱该往哪儿放?」(给依据和建议,不替人定)

## 什么时候不用

- **问活动本身的信息**(什么时候、送什么、怎么报名)—— 直接答或查知识库,不走复盘
- **问渠道单量 / 客单价** —— 调 `channel_compare` 就行
- **问营收为什么变了** —— 那是指标诊断,活动只是可能的原因之一
- **要求直接改活动、发券、改预算** —— 本系统没有这些写口,优惠走审批;这里只出建议

## 用哪些工具(依赖:全是只读,管理视角:店长 / 总部)

- `activity_roi()` —— 全部活动的排名;`activity_roi(code="活动编号")` —— 单个活动明细
- `channel_compare()` —— 渠道表现(只用来说明「渠道和活动拆不开」,不拿来排名)

顾问调 `activity_roi` 会被拒(管理视角),照实告诉他要店长或总部看。

## 第一步:定范围

问清是**哪几个活动**、要回答什么(值不值 / 哪个好 / 钱往哪放)。
用户只说「七夕那个」而对得上的不止一个时,把候选列出来问,不猜。

## 第二步:取数,三种口径并列

调 `activity_roi`。每个活动把这几样**并排写出来**,不只挑一个:

| 成本 | 成交 |
|---|---|
| 预算 / **已发生**(默认) / 已开票 | 应收 / **实收**(默认) / 完成 |

**投入产出比用哪两个口径算的,写在数字旁边。** 「已发生 vs 实收」和「预算 vs 应收」可以差很多,
报一个不说是哪个,看的人会拿它和另一个口径的数比。

## 第三步:把不能算进来的拎出来

- **归因期外的订单**:工具单独报了,**不并进成交**。期外占比高的活动,写一句「要么归因窗口不对、要么活动日期录错」
- **算不出投入产出的**(未开始、已取消):单独列,**不当成 0、不排在最后** —— 「还没开始」和「效果最差」不是一回事
- **活动表上的「报名 / 成交」两列**:是随机数,和订单表无关,**一个字都不引用**

## 第四步:能下什么结论

- 每个活动的成交单数是多少 —— **几单算出来的投入产出比,波动会非常大**,写清单数,单数少的标「样本太小,只看个方向」
- **渠道和活动一一对应**(`channel_compare` 写明了):「这个活动好」和「这个渠道好」在这批数据上分不开,不许拿渠道解释活动
- 有没有**增量**:活动期间成交了,不等于没有活动就不成交 —— 本系统没有对照组,**写成「活动期间成交了多少」,不写「活动带来了多少」**

## 第五步:建议(只是建议)

按这个格式:「依据(哪个口径、几单)→ 建议看 / 试什么 → 还缺什么数据才能定」。
不写「加 20% 预算」「低于 X 倍就停」这种带门槛的话 —— 门槛要业务拍板,不在技能里定。

## 硬规矩

1. **数字只照 `activity_roi` 返回说**,口径写在数字旁边;不自己拿订单数除一除编一个率
2. **不引入任何外部门槛**(保本 ROAS、目标倍数、预算增减比例)
3. **归因期外的不并进成交;算不出的不当 0**
4. **随机列不引用**(活动表的报名 / 成交)
5. **相关不写成因果**:「活动期间成交」≠「活动带来」
6. **不执行任何动作**:改活动、改预算、发券都不是这个技能的事

## 出错了怎么办

- **工具返回「管理视角」拒绝** → 告诉对方这个要店长或总部看,不绕
- **找不到那个活动** → 列出 `activity_roi()` 里名字相近的几个让他选;一个都对不上就说没有这条记录,**不说成「效果为零」**
- **活动全都算不出**(都未开始 / 已取消)→ 照实说「还没有能复盘的活动」
- **单数太少** → 结论就是「样本太小,下不了结论」,列出要攒到什么程度的数据才能看(比如再跑一期),但不定具体门槛
- **用户追问「那到底该不该停」** → 把依据和缺口摆出来,说明这是要他拍板的决定

## 例子(示例)

问:「这几个活动哪个效果最好?」(下面只是格式示意,**真答时一律照工具返回**)

1. `activity_roi()` → 拿到全部活动的排名
2. 每个活动写:已发生成本、实收成交、投入产出比(已发生 vs 实收)、成交几单、归因期外几单
3. 两个活动未开始 → 单列「算不出:未开始」,不放进排名末尾
4. 结论:「按已发生 vs 实收,A 最高,但只有 3 单,只能看方向;B 有 40% 的订单在活动期外,先核一下活动日期;
   渠道和活动一一对应,分不出是活动还是渠道的作用」
