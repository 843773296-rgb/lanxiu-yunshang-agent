# 澜绣云裳agent · 项目解读报告

第 14 版 · 2026-10-03 · 本次变化:**项目长出了一个「管自己」的系统,而那个系统立刻用同一种方式坏了**

> 第 13 版的结论是:**脚手架也是系统的一部分,而且它坏掉的时候,业务代码看起来是好的。**
>
> 这十天做的事,正好是那句话的下一步:**给脚手架装仪表盘**。
> 管理后台 9-27 第一次提交,十天 **166 个文件 / 4.3 万行** ——
> 占这十天新增代码的**三分之二**,而它一行业务功能都不做:
> 它管 Prompt 版本、知识库、工具目录、旋钮、评测、发布。
>
> 然后发生了这一版要讲的事:**仪表盘自己也会坏,而且坏法和它要监控的东西一模一样。**
>
> 十天里被抓到的,挑五个:
>
> · 后台的「评测中心」能建评测、能人工复核、能列表、能对比 ——
>   **但没有任何一条口能把跑完的结果写回来**。建一个评测,然后它永远排队
> · 「探测连接」那条口写着 `探法: "真实端点"`,而它**全程没碰过网络** ——
>   读一下适配器契约、写一行字、落库
> · 筛选策略上那个「开独立路由」的开关,**一道闸都没有** —— 只是 `bool()` 收下来,
>   而规格原文要的是「**只有实验证明额外分类有价值时才启用**」
> · 一条同步判据报「文件改了没重导」,而真相是**另一个会话有 4 行没提交的改动** ——
>   照着提示导下去,就是把别人的半成品灌进后台、还给它发一个正式版本号
> · 「静默截断」那条判据自己漏了三处同形状的 —— 它说「一处没多」,而 grep 一遍就有三处
>
> **这五条的共同形状,和第 13 版那四条是同一个:**
> 一个声称自己做了某件事、而其实没做的东西,在数据形状上和真做了的一模一样。
>
> 第 13 版说的是「尺子之外的脚手架也会坏」。
> 这一版要加的是:**管脚手架的那一层,还是会以同样的方式坏 ——
> 所以「我装了检查」本身不是保证,「我撞红过那条检查」才是。**

## 一、项目由哪几块组成 + 工程体检

### 结构:原来四层,现在**旁边多了一整块**

```
   客户手机端 /m         自助预约、试穿合身码(唯一不用登录的入口)

   智能助手(对话)        6 个角色各拿各的工具

        ↓

        ↓
   数据 99 张表          SQLite,固定种子确定性生成

   ──────────── 以上是「跑业务的」 ────────────

   管理后台(9-27 新建)   PostgreSQL · 166 文件 / 4.3 万行 · 一行业务功能都不做
        ├ Prompt 版本     澜绣那 79 条铁律的版本历史
        ├ 知识库          23 篇语料的文档版本 + 1335 个片段
```

**现在的规模**(现算,2026-10-03):**572 个 Python 文件 / 15.25 万行**(不含依赖)·
git **993 次提交**(9-24 以来 **315 次**)。

## 二、AI 架构在哪一代

### 哪一代:**没变 —— 三代同仓,主力第三代**

| 代 | 在哪 | 指纹 |
|---|---|---|
| 第一代 | `agent/v1.py` | 手写工具调用循环,自己判 `tool_use` 自己执行(严格说是 **1.5 代**) |
| 第二代 | `agent/v2.py` | 流程显式建成图,大部分节点纯规则不调模型 |
| **第三代** | `agentsite/sdk.py` | **Claude Agent SDK**,四个 Hook 全程把关,MCP 挂三个服务器,一个 Skill |

判定依据:`agentsite/sdk.py` 用 `claude_agent_sdk`、`disallowed_tools` 点名封掉自带写工具 +
PreToolUse Hook 拦掉所有非 `mcp__` 的工具(**双锁**)。属于**本地 Harness** 这一支。

### 这一代的特点,以及这十天新暴露的代价

**这十天第一次把「第三代的代价」量成了一个具体的数。**

| | 单条成本 |
|---|---|
| 第二代跑完一整条 | $0.0012 |
| 第一代 | $0.0125 |
| **第三代** | **$0.0286** |

而钱花在哪,这十天查清了:**每一次调用都要把全部工具定义带上**。
81 个工具的完整定义是 **18497 token**;全能助手实际挂 **77** 个。
> **加一个工具的代价不在那个工具上,在此后每一次调用上** —— 而它在功能测试里完全看不见。

### 升代能得到什么 / 最小迁移路径

**已经在第三代了,所以这一版的「升代」问题换成了另一个:怎么把第三代的成本压下来而不损失能力。**

这十天做的正是它,而且**第一次有了数**:

| 做法 | 召回 | 每条额外成本 |
|---|---|---|
| 不筛选(现状之一:全能助手 77 个) | 100% | 0,但每轮带 18497 token 的工具定义 |
| 按角色发工具(现状之二,硬编码) | 100% | 0,候选 5–61 个 |
| 关键词检索 @候选 5 | **54%** | 0 |
| 关键词 + 业务话别名 | **60%** | 0 |
| **独立路由器(小模型选工具)** | **87%** | **$0.00109**(带提示词缓存) |

**路由器一次 ≈ 第二代跑一整条,是第三代的 3.8%。**

⚠️ 一条诚实的缺口:**「省下来多少」没量**。要算净成本得量「开路由器之后主调用的
token 降多少」,那要改澜绣的运行代码,这一轮没做。
> 只报 $0.00109 会把它说成纯支出,而它很可能是净省。**但「很可能」不是数据。**

**最小迁移路径的第一步(没做)**:把筛选接上执行层。
现在后台是「看得见、配得住」——策略版本 `tspv_cec7b4bfa7b7` 已经冻结(只开路由器),
而澜绣跑起来**仍然是按角色发工具**。
> **「让它看得见」和「让它生效」是两步。**

## 三、prompt 在哪、怎么拼的

### 单一源头没变,而这十天它第一次被「版本化」了

`prompts.py` 仍是唯一源头,79 条铁律按工具装配,P1–P6 六条结构检查顶着
(其中 **P6:挂了某个工具就必须拿到管它的那条规矩** ——「工具给了、规矩没给」比「工具没给」更危险)。

新的是:这 79 条现在**在后台里有版本历史**。十天里 TL02 / TL31 / TL34 各出过 v2。

### 一次调用的成本账(记录仪现算,全量 5506 次)

```
  总调用   5506 次 · 累计 $115.89
  9-24 以来 983 次 · $22.67
  输入     12,623,534 token
  输出      6,089,058 token
  缓存命中 584,906,572 token     ← 注意这个数
  缓存写    24,882,170 token
```

**缓存命中占输入的 97.9%。**

这个数是这一版最该看懂的一个。它的意思是:
**我们发给模型的东西里,97.9% 是每次都一样的那一段**(工具定义 + 系统提示词 + 铁律)。

而它正好解释了为什么路由器便宜:路由器的目录每次都一样,是**完美的缓存前缀** ——
实测入 token 从 7343 降到 **31 + 读缓存 7090**,成本 **$0.00741 → $0.00109,压到 1/7**。

⚠️ 而它同时解释了一个边界:**不开缓存,最慢那些请求会超时**。
实测同一批题,不带缓存最慢 **4438ms**、带缓存 **2743ms**,而规格的筛选超时预算是 **3000ms**。
> **提示词缓存不只是省钱,它是那个超时预算成立的前提。**

按模型:haiku-4-5 **4766 次 / $95.63** · sonnet-5 418 次 / $17.36 ·
deepseek-v4-pro 311 次 / $2.12(9-15 那一轮,已存档不许当基线)· opus-5 11 次 / $0.78。

## 四、检索与评测现状

### a. 检索:**这十天第一次回答了「该不该用」,而答案是「先别」**

规格支持四种工具检索模式,首版只允许两种:固定工具组、关键词检索;
混合检索(要向量)明写是扩展、**按同题结果再启用**。而两家模型都没有 embedding API。

关键词检索实测了,结论是**瓶颈不在算法上**:

| | 候选 5 | 候选 20 |
|---|---|---|
| 字 bigram 重叠 | 17/21 | 18/21 |
| 加 idf 权重 | 18/21 | 18/21 |

**加大候选上限一个都没多捞到。** 去掉截断看全 77 名的排名 —— **5 题的需要工具一个都没进排名**:

```
 阔褶马面裙(PT05)有 S 码吗?        → 需要「版型库」,和问法**一个共同片段都没有**
 灰缬能做在浅色棉麻上吗?            → 需要「相容矩阵」,没有
 我今天有什么活?                   → 没有
 今天该我核什么?                   → 没有
 PT01 这个版型的裁片用料占比是多少?  → 没有
```

「零重叠」的意思是**分数是 0**。换打分法、加大候选、调权重 —— 全都无效。

> **用户问的是业务,工具说明写的是系统。**
> 用户说「还能发几件」「到哪一步了」;说明说「查现货」「查订单」。**字面不重叠。**
> 所以**关键词检索在这里真正检索的是「用户恰好用了说明里的词吗」** —— 而用户不读说明。

这和这个项目在中文否定上栽过七次的那条是**同一个病的产品化版本**:
按词表判「有没有说某个意思」,真正判的是「用了我这几个词吗」。

### b. 评测:**22 个评测集,而这十天最大的进步是学会了不相信自己的题**

新增 4 个评测集 + 2 个探针(`select_eval` / `select_probe` / `router_probe` / `oppo_eval` …)。

**而这一版真正的收获是一次自我纠正:**

我为「工具选得对不对」造了 21 道题,量出关键词召回 **86%**。
后来换成一个**不是为检索造的**留出集(`tool_eval` 那 22 题 + `tool_routing` 那 11 题),
同样的算法只有 **54%**。

**差 32 个百分点。** 而高的那个是虚高的:我那 21 题是从工具说明里 51 处
「⚠️ 别跟我搞混」挖出来的 —— **天然偏向字面重叠**。

> **我差点拿 86% 当选型依据。**

同一天还栽了一次更隐蔽的:我拿「漏掉的那 3 道题」**反推**出别名表,得到 21/21。
那是**先看答案再出题**。换到留出集上,同一份别名只值 6 个百分点,而且在候选 10 以上**一个点都不值**。
> **不符合预期的数会被查,符合预期的数会被信。**

**三大鸿沟定位**(evals-map 的框架):这个项目现在卡在**第一条「理解鸿沟」** ——
不知道用户真会怎么问。证据:81 个工具里只有 **47 个**有任何真实问法记录,
而 `kb_*` 那一族(工艺/面料/工期/BOM/相容矩阵)**一条都没有**,
因为那条线的评测要么不记轨迹、要么没判过。

⚠️ 还查出一个**真值过期**的问题:`agentsite/evals/tool_routing.json` 那 11 道题的期望里,
**8 处是合并前的旧工具名**(`my_tasks` / `team_tasks` / `member_level` / `get_lifecycle` /
`get_member_priority` / `get_task` / `dispatch_pool` / `piece_ratios`),都已不存在。
每条都至少有一个名字还活着,所以没有一题是量不了的 —— **但下次用它之前要再核一遍**。
> 一个真值指向已不存在的工具的评测题,和一道正常的题,**在成绩单上长得一模一样**。

## 五、建议接下来学什么

### ① 「我装了检查」不是保证,「我撞红过那条检查」才是(最该学的)

这十天最值钱的一条教训,来自**判据自己骗人的五种方式**,每一种都在这个项目里真发生过:

| 坏法 | 现场 |
|---|---|
| **断言靠提示文案里恰好有几个字成立** | 「传工具连接 id 也红」那条,传的是一个不存在的 id —— 而错误提示**永远带着**「不是工具连接」几个字,所以它过了 |
| **排除集一个都没排掉** | 排除集写的是打印用的显示名(`BR8`),而数据里是 `R8` —— 于是「可答的」照样印出一个数(81%,真数 87%) |
| **一次注入两个破坏,只验到一个** | 前面的闸先拦住,后面那道根本没走到,而输出看起来像「全红了」 |
| **破坏点不可观测** | 咬合时改的是 `messages`,而判据比的是 `content_hash` —— 那次「没红」说明不了任何事 |
| **断言管得太宽** | 「没发请求的必须说为什么」—— 而 mock 没发请求是**按设计**,不是失败 |

**怎么学**:每写一条检查,问三句话 ——
① 我撞红过它吗?② 撞的那一下**只破坏了一件事**吗?③ 这条检查**漏掉的那几处**,和不存在的那几处,我分得清吗?

出处:这是本项目的经验判断,没有权威出处。但同族的工程实践叫 **mutation testing**
(故意改坏代码、看测试会不会红),可查 Papadakis 等《Mutation Testing Advances》综述(2019)。

### ② 提示词缓存:97.9% 这个数该怎么用

你的记录仪说输入里 97.9% 是缓存命中。这意味着**成本结构和直觉相反**:
不是「少说话省钱」,而是「**把每次都一样的那段固定在最前面**」。

实测:路由器的目录固定在 system 段最前 → 入 token 7343 降到 31,成本降到 1/7。
而顺序一动,缓存就全失效 —— 渲染顺序是 **tools → system → messages**,
所以能缓存的只有「工具说明书 + 系统提示词」那段**每轮都一样的前缀**。

一手出处:Anthropic 官方文档 Prompt caching 一节(`docs.anthropic.com` → Prompt caching),
里面写明缓存是**前缀匹配**、`cache_control` 标在哪一块之前的内容才会被缓存。
**值得你亲手读一遍那一页** —— 它直接决定你这个项目的成本量级。

### ③ 「理解鸿沟」:别名表该从哪来

第四板块那个数说清了:81 个工具里 **34 个没有任何真实问法记录**。
而关键词检索失败的 5 题,全是「用户的话和工具说明零重叠」。

**这不是算法问题,是你还不知道用户会怎么问。** 这正是三大鸿沟里的第一条。

可做的最小一步:从客服通话逐字稿里挖 —— 你项目里 `call_opportunity` 这个工具
读的就是**真实通话逐字稿**。那是这个项目里**唯一一处真用户语料**,
而它现在只被用来找商机,没被用来改进工具说明。

出处:evals-map 的「先定性(人看 case),再定量(打分)」—— 而你现在缺的是定性那一步。

## 附:这一版之后,项目还欠着什么

- **筛选没接上执行层**。后台配好了(`tspv_cec7b4bfa7b7`),而澜绣跑起来仍是按角色发工具

- **`make test` 还有一条真约束红**(`embeddings` 要空)—— 那是前提,不是 bug
- **`tool_routing` 那 11 题的真值要重核**(8 处旧工具名)
