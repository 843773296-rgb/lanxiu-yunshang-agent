# 澜绣云裳agent · 项目解读报告

第 13 版 · 2026-09-24 · 本次变化:**这一周把四条业务硬规矩从「提示词里说说」搬到了「状态机上拦住」;而同一周的四次翻车,全都来自我们自己搭的脚手架**

> 第 12 版说的是「尺子会在你不看的时候坏掉」。
>
> 这一版说的是**尺子之外的东西**:我们自己往模型上下文里塞的那句话、我们自己写的检查、
> 我们自己造的演示数据、我们自己的判分器 —— 这四样都不是业务代码,都是**为了保证质量而搭的脚手架**,
> 而这一周的四次翻车,没有一次来自业务代码,**全部来自脚手架**:
>
> · 我们自己的钩子每轮往模型上下文里塞「今天是〈机器日期〉,一律以这一天为准」——
>   而演示世界的今天比机器早三周。结果:逾期 3 天被答成「已晚 25 天」,而且**读起来完全合理**
> · 我们自己的守卫把「使用技能」整个拦掉了,于是**自家 6 个技能的正文从来没被加载过**,
>   而技能评测只看「模型想不想调」,所以一直显示正常
> · 我们自己的写冒烟检查**写进了真库**(把唯一一张分批发的单退了一档),
>   于是两边的夹具同时失去样本,而两处红都显示「取不到样本」,**谁也看不出真凶**
> · 我们自己的判分器把全角问号写成了半角,于是模型**问了**也被判成「没问」,四套评测同时中招
>
> 上一版的结论是「每隔一阵回头问一次这把尺还准不准」。
> 这一版要加的是:**脚手架也是系统的一部分,而且它坏掉的时候,业务代码看起来是好的。**

## 一、项目由哪几块组成 + 工程体检

### 结构:四层没变,量变了

```
   客户手机端 /m      自助预约、试穿合身码(唯一不用登录的入口)
        ↓
   智能助手(对话)     5 个角色各拿各的工具:门店顾问 / 版师核料 / 工坊排产 / 后台运营 / 全能
        ↓
   工具层 73 个       读 52 · 写 21 —— 写的那 21 个全部登记在册
        ↓
   业务口径 37 个模块  判定规则只住在这里,工具只负责取数
        ↓
   数据 91 张表       SQLite,由固定种子确定性生成,23 步重建
```

**现在的规模**(现算,2026-09-24):344 个 Python 文件 / 9.0 万行(不含依赖)· git 676 次提交,
**其中 312 次是最近一周的** · `check.sh` 里 172 条检查 · 23 套评测结果存档在版本库里。

### 这一周新长出来的那一段:生产和交付

以前订单走到「待生产」之后,后面几档是**在后台手点**过去的。这一周补完了:

| 环节 | 现在靠什么成立 |
|---|---|
| 开裁 | 该试白坯的试过、**客户签了字**才许裁 |
| 生产 / 发货 | **只认工厂回传**,门店和后台都推不动;可以分批发货,每个包裹独立 |
| 发错件 / 到店返工 | **只有店长能人工回退**,必须写理由,运费公司承担 |
| 工厂撤回 / 更正 | 只能改时间和快递单号;撤回**不自动退订单状态** |
| 整批延期 | 按新完工日判超期,**原承诺日和延期次数一直留着** |
| 到店签收 | 按**件**签收:合身的当场拿走,不合身那件留店转返修 |

### 七环体检

| 环 | 判定 | 现场证据 |
|---|---|---|
| **需求** | ✅ | 业务口径写进 `knowledge/` 而不是聊天记录:这一周新增 `factory_feed.py`(工厂回传)、`order_place.py`(下单)、`muslin.py`(白坯)。每条规矩都标着「业务 09-22 / 09-23 确认」,**哪条是业务定的、哪条是我提的建议值,分得开** |
| **架构** | ✅ | 判定和取数分层没破:工具只取数,判定在口径模块(37 个)。新加的工厂回传严格照这个分:`knowledge/factory_feed.py` 不碰库、不取当前日期,`backend/factory_inbox.py` 只负责落库 |
| **实现** | ✅ | 8 道闸挂在**订单状态机**上,不是挂在入口里:白坯、下单量体、签收、完成、返修两道、工厂回传、人工回退。**后台那个通用「改状态」入口绕不过它们** |
| **验证** | ⚠️ | 172 条检查 + 23 套评测。但这一周有四次是**脚手架自己坏了**(见开头)。新功能的检查是齐的(工厂回传 44 条、下单 22 条、签收 57 条),**评测还没跟上**:分批发货、人工回退、撤回更正、延期通知,四样一道评测题都没有 |
| **部署** | ⚠️ | 两条命令能起;CI 每次从零建库跑门禁。**这一周红过三次,全是「本地绿、CI 从零红」** —— 本地留着历次产物,CI 不留,两者只在「从零建得起来」这件事上分岔 |
| **运维** | ✅ | 每张订单有**独立日志**:状态变化、每条工厂回传(**含被拒收和作废的**)、人工回退、延期、按件签收,按时间排成一条 |
| **迭代** | ✅ | 676 次提交,每次写清「为什么这么改、踩了什么坑」;产品需求文档里 **81 条难点记录、243 条算法记录**(现算) |

**体检里最值得说的一条:** 「验证」这一环从 ⚠️ 到 ✅ 的距离,不在于再加多少条检查,
而在于**检查本身有没有人验**。这一周的四次翻车里,有三次是检查/判分器/造数自己的问题,
而它们在出事前都显示「绿」。

## 二、AI 架构在哪一代

### 哪一代:三代同仓,主力在第三代

- **第一代(直接调用)**:`agent/v1.py` —— 自己写循环、自己判要不要调工具、自己执行。
- **第二代(工作流编排)**:`agent/v2.py` —— 流程显式建成图,大部分节点是纯规则,**每条只调 1 次模型**。
- **第三代(Harness)**:`agentsite/sdk.py` —— 模型自己规划,循环、工具、预算、钩子由 harness 管。

**这个项目真正少见的地方不是做了第三代,是三代在同一个仓库、同一批题上可以横着比。**

### 这一代的特点,以及这一周暴露的代价

第三代把「循环怎么转」交给了别人,换来的是模型能自己规划多步。代价这一周结结实实撞到两次:

1. **上下文不是你一个人在写。** 除了你的系统提示词,harness 和你自己的钩子都会往里塞东西。
   这一周那个「晚 3 天说成晚 25 天」,根因就是**我们自己的钩子**每轮注入机器日期,
   而且用的是命令口气,**压过了后加的规矩**。
   > 一句话:**第三代里,「模型看到了什么」不再等于「我写了什么」。**

2. **工具越多,每次调用越贵。** 记录仪现算:9 月 17 日以来 2043 次调用,合计约 \$51.6(估算),
   第三代单次调用**平均缓存命中 17 万 token**、单次约 \$0.029。
   而第二代大部分节点根本不调模型。
   > **「加一个工具」的代价不在那个工具上,在此后每一次调用上** —— 而功能测试里完全看不见。

### 升代能得到什么 / 最小迁移路径

这个项目不需要升代,它已经在第三代。真正的下一步是**把第三代用对**:

- **该停在第二代的别硬上第三代**:步骤能提前枚举的活(比如排班、批量派工),第二代更可控更便宜。
- **把「谁往上下文里写东西」管起来**:现在没有任何东西会发现「两处注入互相打架」——
  日期那次是靠评测里一句原话露出来的。**这是我建议的下一个练习。**

## 三、prompt 在哪、怎么拼的

- **单一源头**:根目录 `prompts.py`,71 条规矩,**按工具装配** —— 挂了哪个工具,就发管它的那条规矩;
  没挂的不发(结构检查 P6 强制)。
- **按角色发工具**:门店顾问 37 个、后台运营 53 个、工坊 7 个、版师 9 个。
  以前是整包发,一个角色能看见别人的工具。
- **这一周新加的规矩**:确认下单等于登记已收款(不清楚付没付先问)、工厂回传那三条(不许建议后台手改、
  不替工厂补数据、催工厂是人的动作)、业务上的今天是哪天。

### 一次调用的成本账(现算,9 月 17 日以来)

| | 第三代 |
|---|---|
| 调用次数 | 1696 次 |
| 单次缓存命中 | 平均 **16.97 万 token** |
| 单次成本 | 平均 **\$0.0288** |

**缓存命中越高不代表越省** —— 它说明每次都把同一大坨东西(工具定义 + 规矩)重新带上一遍。
省钱的办法不是加缓存,是**少带**:按角色发工具就是这么省下来的,而这个收益**至今没有专门测过**
(🔮 预计财务那条线每轮省两万 token 左右 —— **没验**)。

## 四、检索与评测现状

**检索**:这个项目没有向量检索,知识库是手写的 14 篇 md + 推导脚本生成的派生数据,
工具按结构查表。**这是对的选择** —— 业务问的是「这个工艺能不能配这个面料」,
答案要能说出依据、能对账,不是「找几段相似的话」。

**评测**:23 套结果存档在版本库里。这一周跑过的:

| 评测 | 两轮 | 说明 |
|---|---|---|
| 工厂回传 | 6/6 · 6/6 | 这一周新写的 |
| 交付签收 | 7/9 · 9/9 | |
| 量体录入 | 7/8 · 7/8 | 判分器修好后比修前高一题 |
| 成长推算 | 6/8 · 7/8 | 挂的两题都是「一个工具都没调就答」 |
| 会员 | 11/12 | |

**评测这一环最该补的两处:**

1. **四样新功能一道题都没有**:分批发货、人工回退、撤回更正、延期通知。
   现在只有代码层面的检查(44 条),**没测过真模型会不会用错** ——
   比如有人对助手说「帮我把这单退回去」,它会不会照做而不看是谁在说话。
2. **技能放行之后的基线要重新认**:2026-09-23 之前所有评测跑的都是「技能没生效」的版本。
   那些分数不作废,但**和以后的数不可比**,文档里要注明日期。

## 五、建议接下来学什么

### ① 上下文注入的冲突检测(最该做的)

**为什么**:这一周最贵的一次翻车,不是模型不行,是**我们自己往上下文里塞的两句话互相打架**,
而系统里没有任何东西会发现这件事 —— 它是靠评测里一句「现在 9 月 22 日」露出来的。

**练习**:给项目加一条检查 —— 把所有往模型上下文里注入内容的地方列出来(系统提示词、
开场注入、技能正文、工具描述),看有没有两处对**同一件事**给出不同指令。
先从最容易冲突的三类入手:日期、权限、数值口径。

**出处**:Anthropic《Effective context engineering for AI agents》(官方工程博客,一手)。

### ② 「意图」和「效果」是两个评测对象

**为什么**:技能被拦那件事挂了很久没人发现,**因为评测测的是「模型想不想调这个技能」,
而不是「技能真的加载之后答得对不对」**。前者是意图,后者是效果,两者可以长期背离。

**练习**:挑一个技能(比如报价),写两道题:一道测它该不该触发,一道测**触发之后**
产出的报价单有没有把该说的都说了。跑两轮,看两个数是不是同涨同跌。

**出处**:Anthropic《Agent Skills》文档(一手);评测方法部分见 `references/evals-map.md`。

### ③ 脚手架的隔离:检查不许写真库

**为什么**:这一周同一个形状踩了两次 —— 一次是签收那边的检查往真库写了返修单,
一次是我的写冒烟把真库的订单退了一档。根因都是「把模块指到测试副本」时**漏了用到时才加载的模块**。

**练习**:写一条"检查的检查" —— 跑完所有检查之后,比对真库的关键表行数有没有变。
变了就红,并且报出是哪一条检查干的。

**出处**:这条是经验判断,没有权威出处。
