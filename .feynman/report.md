## 一、你的项目由哪几块组成

```
        浏览器(4 个页面,原生 JS,零外部依赖)
            │  HTTP
   ┌────────┴─────────────────────────────────────┐
   │  后台服务  backend/server.py  单文件 1100+ 行 │  ← 门房:所有请求都从这进
   │  ┌──────────────────────────────────────────┐│
   │  │ api.py     10 个只读接口 ← 智能体的「手」  ││
   │  │ fsm.py     状态流转引擎,15 台状态机       ││  ← 规矩:什么能流转到什么
   │  │ rules.py   写入校验(重复手机号/预约提前量)││
   │  │ lanxiu.db  SQLite,36 张表,固定种子生成   ││  ← 仓库
   │  └──────────────────────────────────────────┘│
   └───────────────────────┬──────────────────────┘
                           │
   ┌───────────────────────┴──────────────────────┐
   │  智能体  agent/                               │
   │   v1.py    手写的工具调用循环 ← 唯一的模型出口│
   │   chat.py  工艺顾问(复用同一个循环)          │
   │   eval / negative / chat_eval  三套评测集     │
   └───────────────────────┬──────────────────────┘
                           │
   ┌───────────────────────┴──────────────────────┐
   │  知识层  knowledge/  10 份 md(人维护)        │
   │   kb.py 解析 → craft 表(机器读)· 单向不回写  │
   └──────────────────────────────────────────────┘
```

四块的关系,用一句话说清:

- **后台服务**是门房。浏览器要什么都找它,它转身去问引擎或仓库。整个项目**没有装任何第三方库**,纯 Python 自带的东西(`find` 未发现 requirements.txt / package.json)。这在今天很少见,好处是「换台电脑就能跑」。
- **状态流转引擎**是规矩。它管的是「已付的押金能不能退回未付」这类问题 —— 15 台状态机,非法流转一律拒绝并说明理由。
- **智能体**是两个:一个替财务查退款为什么失败,一个替顾问答汉服工艺问题。它们共用同一段循环代码(`agent/v1.py:73` 的 `run_case`)。
- **知识层**是 10 份 Markdown。**人在 md 里写,机器读的表由解析器生成,单向,不回写** —— 这样同一份知识不会存两遍、也就不会漂移。

**② 「什么进版本库」的判断标准,不是「是不是代码」,而是「丢了能不能一模一样地再造出来」:**

| 东西 | 能不能重造 | 进不进库 |
|---|---|---|
| `backend/lanxiu.db`(480 K) | 能 —— `seed.py` 固定种子 | ❌ 不进 |
| Figma 原始 JSON(1.25 G) | 能 —— 凭 token 重新下载 | ❌ 不进 |
| **`agent/*-results.jsonl`(评测结果)** | **不能** —— 重跑模型会给出不同答案、不同成本 | ✅ **进** |

第三条最容易搞错。评测结果看起来像「跑出来的临时文件」,实际上它是
**一次不可复现的观测,和实验记录本同一性质** —— 丢了它,下次换模型时就没有基准可比。

**提交的是绿的状态**:两个项目提交前都先跑了 `check.sh` 确认全绿,
这样以后任何时候 `git checkout` 回来都是能跑的。

## 二、你的 AI 架构在哪一代

**判定:第 1.5 代 · 手写工具调用循环。** 代内形态:单智能体、多轮工具调用、无编排框架。

### 1. 哪一代(证据)

`agent/v1.py:73` 的 `run_case` 是一个手写的 `for` 循环:发请求 → 看模型要不要调工具 →
调完把结果塞回去 → 再发。没有 import 任何编排框架(无 LangGraph / Dify / Agent SDK),
HTTP 也是自己用 `curl` 发的(`agent/v1.py:52`,因为这台机器的 Python TLS 会被中间人拦截)。

按代际地图的说法,这叫 **1.5 代**:**有 Agent 的灵魂、没有编排的身体** ——
模型确实在自己决定查什么(不是人写死的流程),但循环、上下文、工具全是你自己写的。

### 2. 这一代的特点

- **优势**:每一步都看得见、都能改。你这个项目之所以能查出「模型猜错编码」这种 bug,
  正是因为循环是你自己的 —— 轨迹里记了什么由你决定。
- **天花板**:上下文管理全靠自己。现在每次任务重新开始,**没有压缩、没有会话恢复、
  没有跨任务记忆**。任务一长就会撞上下文墙,而你手上没有工具应对。

### 3. 升第三代(Harness)你会得到什么

具体到你的场景:

| 现在做不了/费劲的 | 三代白送 |
|---|---|
| 五份 Figma 合计 **1.33M token**,V1 根本塞不进去 | 自动压缩,超窗任务能跑完 |
| 任务中断就得从头来 | 会话恢复 |
| 想让它读本地文件/跑脚本,得自己写工具 | 内置文件读写、Bash、搜索 |
| 一个模型串行干完所有事 | 子智能体并行 |

**代价要说清楚**(帕鲁打工仔项目的实测数据):三代比一代**贵 8.9 倍**,
因为每轮重发的系统提示词和工具说明书是固定开销,**任务越简单这个占比越夸张**。

**例外清单核对**(什么情况该留在低代):你**不命中任何一条** ——
这两个智能体的步骤**不能提前枚举**(查完押金才知道要不要查流水,看完流水才知道要不要查客户)。
所以按训练营立场,你属于该走向第三代的那 90%。

### 4. 最小迁移路径

**第一步(一天的事)**:把 `backend/api.py` 里那 10 个只读接口包成一个 MCP 服务。
然后 `agent/v1.py` 那段循环整个删掉,换成 Agent SDK 的 `query()`。
你的工具、评测集、判分器**一个字都不用改** —— 它们本来就和循环解耦。

> 你这个项目的迁移成本异常低,原因是当初工具层就是独立文件(`api.py`)。
> 这是好架构给你的红利:**换掉一整代架构,只动一个文件。**

## 三、你的 prompt 在哪、怎么拼的

### 位置与成分

| | 位置 | 长度 | 成分 |
|---|---|---|---|
| 退款定因 | `agent/v1.py` SYSTEM | 296 字符 ≈ 184 token | 角色 + 4 条铁律 |
| 工艺顾问 | `agent/chat.py` SYSTEM | 1045 字符 ≈ 653 token | 角色 + 6 条铁律 + 回答风格 |
| 题面 | `BP01` / `BP02` 模板 | 68–75 字符 | 动态:押金单号 / 客户ID |

- **固定骨架**:角色定义 + 铁律(不许编、查不到要说查不到、不许绕审批、没有写权限)
- **动态部分**:只有题面里的单号或用户问题
- **示例**:**没有**(zero-shot,即不给例子直接让它做)

### 拼接顺序:对的,但有一处白扔的钱

顺序是 `system(固定)→ tools(固定)→ messages(变动)`。**这个顺序是对的** ——
稳定的东西在前,变动的在后,这正是能命中缓存的排法。

**但实测 118 次调用,缓存命中 = 0。**

```
输入 377,898 token   输出 34,359 token   缓存命中 0
输入是输出的 11.0 倍
```

**输入是输出的 11 倍**,说明绝大部分钱花在「每轮把同样的东西重发一遍」上:

```
每次调用重发的固定部分:
  系统提示词  653 token
  工具说明书  941 token          ← 工艺顾问的 5 个工具
  ─────────────────
  ≈ 1,600 token × 118 次 = 约 19 万 token 是重复的
```

> ⚠️ **但我不能承诺开缓存就一定省。** Anthropic 的提示词缓存有「最小可缓存前缀」门槛
> (随模型不同在 512–4096 token 之间),你这 1,600 token 可能**够不着 Haiku 的门槛**。
> 所以这是一件**要先量再做**的事,不是照着抄配置就行。
> (出处:Anthropic 提示词缓存文档 https://docs.anthropic.com;门槛数值须按当前文档核对)

### 结构化输出:你已经在正确的那一级

退款定因用 `submit_finding` 这个工具的 schema 强制结构(`agent/v1.py:54`),
**而不是在提示词里求它「请输出 JSON」**。

这两者差一个等级:求它输出 JSON,它有时会多写一句「好的,以下是 JSON:」把解析搞崩;
用工具 schema,格式是 API 层面保证的。**你走的是对的那条。**

工艺顾问是纯文本输出 —— 这是对的,因为它的产出是给人读的话术。

### 成本账

实测 48 次任务的真实数字:

| | 数值 |
|---|---|
| 平均每任务 | **$0.0115** · 10.6 秒 · 2.5 次模型调用 |
| 每次调用输入 | 3,203 token |
| 48 次任务总计 | $0.5497 |

**推算**:假设 20 个顾问每人每天问 30 次 = 600 次/天

```
600 × $0.0115 ≈ $6.9/天 ≈ $207/月 ≈ ¥1,500/月
```

这个量级对一个能省下「顾问跑去问工艺师傅、来回两三天」的工具来说,是划算的。
真正需要盯的不是单价,是**调用次数会不会失控**(比如做成每次页面加载都调一遍)。

## 四、检索与评测现状

### a. 检索:你有知识库,但**没有用 RAG,而这是对的**

「RAG」是把文档切块、转成向量、按语义相似度捞回来的做法。你**一点没用** ——
`api.py` 里全是 SQL 精确查询和关键词 `in` 匹配。

**判断:现在不该上 RAG。** 理由三条:

1. 你的知识是**结构化的**(60 个条目、每条有分类和来源等级、外加一张相容矩阵),
   而 RAG 擅长的是非结构化长文本
2. 精确查询**可解释**:`kb_combo(妆花, 云锦) → 可`,依据是哪一行清清楚楚。
   向量检索给的是「最像的三段文字」,说不清为什么
3. 便宜、快、不会「捞回相近但不对」的东西

**什么时候该重新考虑**:条目上千条,或者要检索的变成自由文本
(比如把工艺师傅历年的经验笔记也纳进来)。**到那天再上,现在上是过度设计。**

### b. 评测:三套,是我见过的同阶段项目里做得最认真的

| 评测集 | 题数 | 成绩 | 有没有负向题 |
|---|---|---|---|
| 退款定因(正向) | 20 | 18/20 = 90% | — |
| 退款定因(负向) | 8 | 5/8 = 63% | ✅ |
| 工艺顾问 | 20 | 20/20 | ✅ 6 题(30%) |

**做对的三件事**:

1. **有负向题**。绝大多数项目只测「该做的做对了没」,不测「不该做的有没有不做」。
   你的负向题抓到了真问题:一张证据残缺的单子,模型给了置信度**高**并编出完整因果链
2. **判分器有自测**。chat 那套重判后 20/20,而三条翻转全在往通过方向 ——
   这是过拟合的典型特征。你另建了 `chat_eval_judgetest.py`,喂 18 条人造答案验两个方向,
   **这才是 20/20 可信的依据,不是分数本身**
3. **判据落在客观事实上**。相容类问题比对「结论和工具返回的 verdict 一不一致」,
   而不是「答案里有没有某个词」

**三个缺口**:

| 缺口 | 说明 |
|---|---|
| **样本量 n=1** | 每题只跑一次。模型有随机性 —— 实测中 N7 那题两次跑出了不同结果。**现在的分数说明得了数量级,说明不了稳定性** |
| **没分「能力集」和「回归集」** | 应该分两套:能力集难、暴露不足(理想分 60);回归集发版必过(理想分 90+)。现在混在一起 |
| **相容矩阵完成度 6%** | 273 格填了 16 格。「查不到」在真实使用中会非常频繁,而那正是最容易诱发编造的场景 |

## 五、建议你接下来学什么

按紧急程度排,只挑三个。

### ~~1. 给项目建 git~~ ✅ 本版已完成

两个项目均已建库并完成首次提交。**但「建了仓库」只是第一步,养成习惯才算数**:

- 每完成一件事提交一次,不要攒到最后一把
- **要 AI 大改之前,先提交一次** —— 这是这个后悔药最主要的用法
- 现在是 1 次提交;下次刷新报告时我会看这个数字有没有涨

> 出处:训练营《AI 时代软件工程知识图谱》第 3 章「工程安全网」;
> 真实事故参考 GitLab 2017 误删生产数据库(有备份意识 vs 没有,差别就是一夜和一个月)

### 1. 装调用级记录仪 + 量一次缓存(现在最紧急)

现在只有任务级数据。加一层记录,每次模型调用写一行:
时间、模型、输入/输出 token、**缓存命中数**、耗时、成本。

**这件事的直接收益是回答第三节那个悬着的问题**:开缓存到底能不能省 ——
只有 `cache_read_input_tokens` 这个字段能告诉你答案,而现在你根本没记它。

> 你可以直接跟我说「装记录仪」,这是费曼的一个专门栏目。

### 2. 把相容矩阵从「查得到」变成「拦得住」

这是我们刚才聊到一半的那件事。现在矩阵只有顾问主动问 chat 时才会被读到,
而真实场景里顾问**想不到要问**。

学到的东西:**Tool 和 Hook 的分界线** —— 同一份知识,挂在 Tool 上是「查得到」,
挂在 Hook 上才是「拦得住」;分界的判据不是技术,是**这件事会不会有人主动去问**。

> 出处:Anthropic《Building Effective Agents》
> https://www.anthropic.com/engineering/building-effective-agents

## 附:这个项目做得好的地方(别只看问题)

1. **验证环强得反常**。7 项自动检查、3 套评测、判分器自测 —— 而且每次修完检查器,
   你都会塞一个真的坏东西进去复验它还会不会失败。**这个习惯比任何一项检查本身都值钱。**
2. **知识层单向生成**。md 是唯一源头,表由解析器生成。多数人会两边各存一份,然后半年后发现对不上。
3. **来源分层**。60 条知识每条都标了 public / scale / demo。
   「哪些能对客户说」这件事被做成了可查询的字段,而不是靠人记。
4. **零依赖**。整个项目只用 Python 标准库,换台电脑就能跑。
5. **提交的是绿的状态**。两次首提交之前都先跑了全套检查确认通过 ——
   这意味着版本历史里的每一个点都是「能跑的」,而不是「当时刚好写到这」。
