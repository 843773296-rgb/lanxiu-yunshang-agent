二、本版最重要的一件事:没有分母的「没问题」,不是信息

这一版撞见的洞,形状惊人地一致:系统没有报告任何问题,而问题确实存在 ——

因为「没发生的事」不留痕迹。

#看起来实际上分母是什么
1换个数据库,认出率 93%、0 违规数据全错了断言只生成了 31 条(原本 341 条)
2差集清单每一条都是真的只覆盖了不到三分之一11 条已知规则只撞到 3 条
3定向构造「撞出了三条规则」归因全是错的基线自己就违规,每个变异都在触发它
4咬合测试没变红破坏点从没被执行到那条路径本轮一次都没走到
5自测全绿有两条检查永远成立我自己写的 or True
6靶子上跑得好好的有一整条规则不存在靶子比真实现少读了一个参数

共同点:每一条都不报错,而且都"有结果"。 第 3 条尤其阴 ——

它看起来有结果(三个错误码"撞出来了"),比没有结果更骗人。

修法只有一种:先问「本该有多少」

每一条的修法都是同一个动作 —— 把分母显式说出来:

  • 差集清单 → 报覆盖率:「撞到 2/5,没撞到 BAD_PHONE、NEED_REVIEW、BAD_ADVISOR」; 规格没声明全集时,明说「覆盖率无法度量,别把这份清单当完整规则表」
  • 定向构造 → 报每张表试了几次:「试了 2 次就没戏」和「试了 30 次确实撞不到」不是一回事
  • 咬合测试 → 先证明破坏点真的会被走到(为此专门给靶子加了一条规则, 让「删掉某字段反而成功」这条路径真实存在)
  • 另一条会话独立撞到了同一件事:清空表之后 RFM 的五条性质全部成立 —— 零行数据上什么性质都成立。现在两处加了样本量下限,不够就明说 「是没扫到东西,不是都通过」。
两条线各自独立撞到同一条规律,这件事本身比规律更有说服力。

三、假数据工厂:它到底解决什么问题

上一版只有一句话,这一版补上。

起点:一个真实业务库,声明的外键是 0 个

你这个库 58 张表,一条外键都没明写 —— 关系全靠命名约定和文本 id。

现成的造数工具(Faker 那一类)在这里会找到零个表关系,

造出 58 堆互不相干的孤儿数据:看着有数据,一个 join 都跑不通。

所以工具的核心能力不是"生成",是把没写在 schema 里的关系挖出来:

命名线索 + 值重叠验证(采样这一列的值,看是不是另一张表主键的子集)。

实测 0 个 → 挖出 58 条关系,0.1 秒。

一个贯穿全程的设计:模型只产规则,程序产数据

有两种做法:让模型逐条把数据编出来(慢、贵、跑两次不一样、上不了量),

或者让模型只产出一份方案,由确定性程序执行它。

选了后者。对你来说这意味着:

用户感觉得到的锁死了什么代价
模型产规则秒级出数、要多少有多少、同一个种子永远出同一批数据(bug 能复现)产物是可读可改可进 git 的方案文件,下次不用再调模型方案写错就是批量错

实测:176 万行 / 50 秒 / 741MB,零违规,回滚回到基线。

而整个模型层一共只调了 16 次模型、花了 $0.25。

数据「像」到什么程度,决定能测出什么

档长什么样能测出的问题
结构像字段全、类型对接口跑不跑得通
分布像金额长尾、60% 的客户零订单N+1 查询、空状态、分页错乱
语义像订单状态和时间戳对得上、跨列组合只出现源库有过的业务逻辑 bug

第二档那个「形状」是关键:均匀分布的假数据,这三类问题一个都测不出来 ——

而它们恰恰是线上最常见的三类。

真正不可替代的产出:一张盲区地图

数据库直连绕过业务层,而业务规则大量地不在 schema 里。

你项目的 backend/rules.py 就是活例子:

规则数据库知道吗
手机号标准化后相同 → 阻止新建❌ 那一列不唯一
到店预约至少提前 2 小时❌ 就是两个字符串
客户姓名必填❌ 那一列可空

所以用系统自己的写接口造数,接口每拒绝一条,就等于问出一条 schema 里看不见的规则。

这份「库允许、业务不允许」的差集,就是数据库直连那条路的盲区地图。

而这张地图直接催生了第四节那个发现。

四、智能体编了一套架构理由,而前提全对

拿着差集清单探的第一题:

问:客户到店了但姓名还没问到,能不能先用手机号建个档,姓名回头补?
答:「可以的,系统设计就是这么打的」—— 然后讲了一套账户与门店档案分层的道理。

一个工具都没调。 而校验器返回的是「客户姓名必填」。

最难抓的地方:那套分层是真的存在的。前提完全正确,结论完全相反。

根因是业务写入规则对智能体不可见:它只能凭表结构推断,而表结构给的恰恰是反的。

修法不是把规则抄进提示词(那又是一份手抄件),而是给它一个去跑真校验器的工具。

改后同一题:「不能。业务规则是客户姓名必填。」

同一道差,**对造数工具是「造出库允许但业务不可能的数据」,
对智能体是「答出库允许但业务不可能的结论」** —— 两条线撞的是同一堵墙。

五、模型该用在哪:一个可以直接搬走的分工

假数据工厂里模型只做统计做不到的四件事,这个分工对你自己以后设计产品有用:

交给谁做什么为什么
统计挖表关系、量分布、算「从没同时出现的组合」便宜、稳定、可复现
模型①否决误报 ②认领没语义的列 ③推状态机 ④判「从没见过」是真规则还是样本太小这四件事统计跨不过去
程序照方案造数据要多少有多少

第一件事有个漂亮的实证:两列手机号值重叠 96%,统计上像真外键。

而其中一列的注释写着「这是登录凭据,那个是联系方式,两件事,别合并」。

模型两条都否了,理由直接引注释原文。统计推得出关系,推不出语义。

第四件事更微妙:统计只能说「这个组合一次没出现,而独立假设下该出现 3 次」,

说不出这是业务上不可能还是样本太小碰巧没赶上 ——

46 行数据上这两件事长得一模一样。这道坎统计跨不过去,所以交给模型。

但模型说的每一句都要过校验

不是信不信任的问题 —— 能力边界要在代码里划死,不能靠提示词请求。

实测挡下四类:编出库里没有的状态值、生成器不认识的语义、

一个时间戳列被两个状态共用(会派生出自相矛盾的断言)、

以及"模型写的 SQL 只允许 select count(*)"。

三代同仓,而且三代都是满分。 同 6 条工单、同一个 Claude Haiku:

八、建议你接下来学什么

1. 「分母」这个习惯(半天,不用写代码)

本版所有发现都是一件事:没有分母的「没问题」不是信息。

建议你拿自己项目里的每一份"报告/清单/检查"问三句:

① 它的全集是多少?② 它这次验了几个?③ 「没发现问题」和「没去看」在输出上分得开吗?

(出处:这是从本项目多次真实事故里总结的,没有权威出处 —— 但它就是统计学里的

幸存者偏差在软件里的形态:你只看得见发生了的。)

2. 「兜底方向」——上一版留的,这一版又中了一次(半天)

默认值站在哪一边,决定了「未知」被算成哪一类。

本版新增一例:接口驱动的成败判定原来是「没看到 error 字段就算成功」,

而真实接口返回的是 {ok: false, ...},压根没有 error 字段 ——

于是每一次业务拒绝都被记成成功,而拒绝清单正是这条路唯一不可替代的产出。

兜底方向选错,失败会打扮成成功。

3. 一份真实数据(半天)—— 这条从第 8 版挂到现在,但已经不一样了

上一版说「所有结论仍然建立在假数据上」。现在假数据工厂已经能造出

结构/分布/语义都自洽的数据,并在三个库上验证过(你的库、真 MySQL、

一个刻意处处相反的英文库)。

但反例仍然只能手写 —— 种子里那三条「故意不完整」的数据是三条规则的唯一用例,

而随机生成的数据天然造不出相似性(两条随机记录不会碰巧相似,加到一百万条也一样)。

拿一份真实数据跑一遍野外巡检,仍然是这个项目从「做得很扎实」走向「真的有用」的那一步。

附:这个项目做得好的地方

  • 每一条检查都被亲手弄红过,而且这一版学会了咬合测试自己也会失效的三种形状: 注入没进检查视野 / 破坏点本身没被走到 / 变成崩溃而崩溃看起来像没跑。
  • 「绿」有两种:守住了,和没走到。 而它们在输出上完全一样 —— 所以要么让检查报出"验了多少个",要么先证明破坏点会被执行到。
  • 变异是有参照物的,随机没有。 这句解释了为什么随机数据永远撞不到「相似性」类规则: 缺的不是数据量,是参照物。
  • 两个会话同仓协作,互相照出了对方看不见的洞。 一方报出四个死路由(实测请求直接断连), 另一方报出「预约时间被严格校验、然后没被存下来」;一方的真实现给了另一方 第一个外部参照物,当场照出「每一次业务拒绝都被记成成功」。 自洽不等于正确,得有个不受我控制的东西来对。
