缓存命中占输入的 97.9%

意思是：我们发给模型的东西里，97.9% 是每次都一样的那一段（工具定义 + 系统提示词 + 铁律）。

它正好解释了为什么路由器便宜：目录每次都一样，是完美的缓存前缀 —— 入 token 从 7343 降到 31 + 读缓存 7090，成本 $0.00741 → $0.00109，压到 1/7。

而它同时解释了一个边界：实测同一批题，不带缓存最慢 4438ms、带缓存 2743ms，而规格的筛选超时预算是 3000ms。
提示词缓存不只是省钱，它是那个超时预算成立的前提。

四检索与评测现状

a. 检索：这十天第一次回答了「该不该用」，而答案是「先别」

规格支持四种模式，首版只允许两种（固定工具组、关键词检索）；混合检索要向量，明写是扩展，按同题结果再启用 —— 而两家模型都没有 embedding API。

关键词检索实测了，结论是瓶颈不在算法上：加大候选上限从 5 到 20，一个都没多捞到。去掉截断看全 77 名的排名 —— 5 题的需要工具一个都没进排名：

 阔褶马面裙(PT05)有 S 码吗?        → 需要「版型库」，和问法一个共同片段都没有
 灰缬能做在浅色棉麻上吗?            → 需要「相容矩阵」，没有
 我今天有什么活?                   → 没有
 今天该我核什么?                   → 没有
 PT01 这个版型的裁片用料占比是多少?  → 没有
「零重叠」的意思是分数是 0。换打分法、加大候选、调权重 —— 全都无效。

用户问的是业务，工具说明写的是系统。用户说「还能发几件」「到哪一步了」；说明说「查现货」「查订单」。字面不重叠。
所以关键词检索在这里真正检索的是「用户恰好用了说明里的词吗」 —— 而用户不读说明。

这和这个项目在中文否定上栽过七次的那条是同一个病的产品化版本：按词表判「有没有说某个意思」，真正判的是「用了我这几个词吗」。

b. 评测：22 个评测集，而这十天最大的进步是学会了不相信自己的题

新增 4 个评测集 + 2 个探针。而真正的收获是一次自我纠正：

用哪套题量关键词召回结果

同一天还栽了一次更隐蔽的：拿「漏掉的那 3 道题」反推出别名表，得到 21/21 —— 那是先看答案再出题。换到留出集上同一份别名只值 6 个百分点。
不符合预期的数会被查，符合预期的数会被信。

三大鸿沟定位：这个项目现在卡在第一条「理解鸿沟」 —— 不知道用户真会怎么问。 证据：81 个工具里只有 47 个有任何真实问法记录，而 kb_* 那一族（工艺/面料/工期/BOM/相容矩阵）一条都没有。

⚠️ 还查出一个真值过期：agentsite/evals/tool_routing.json 那 11 题的期望里，8 处是合并前的旧工具名，都已不存在。 每条至少有一个名字还活着，所以没有一题量不了 —— 但下次用它之前要再核一遍。
一个真值指向已不存在的工具的评测题，和一道正常的题，在成绩单上长得一模一样。

五建议接下来学什么

  1. 「我装了检查」不是保证，「我撞红过那条检查」才是（最该学的）—— 这十天判据自己骗人的五种方式，每一种都真发生过： 断言靠提示文案里恰好有几个字成立 / 排除集一个都没排掉 / 一次注入两个破坏只验到一个 / 破坏点不可观测 / 断言管得太宽。
    怎么学：每写一条检查问三句 —— ① 我撞红过它吗？② 撞的那一下只破坏了一件事吗？③ 这条检查漏掉的那几处，和不存在的那几处，我分得清吗？
    出处：这是本项目的经验判断，没有权威出处。同族实践叫 mutation testing，可查 Papadakis 等《Mutation Testing Advances》综述（2019）。
  2. 提示词缓存：97.9% 这个数该怎么用 —— 成本结构和直觉相反：不是「少说话省钱」，是把每次都一样的那段固定在最前面。 渲染顺序是 tools → system → messages，顺序一动缓存全失效。
    一手出处：Anthropic 官方文档 · Prompt caching（缓存是前缀匹配）—— 值得你亲手读一遍那一页，它直接决定你这个项目的成本量级。
  3. 「理解鸿沟」：别名表该从哪来 —— 81 个工具里 34 个没有任何真实问法记录，而关键词失败的 5 题全是「用户的话和工具说明零重叠」。 这不是算法问题，是你还不知道用户会怎么问。
    最小一步：从客服通话逐字稿里挖 —— 你项目里 call_opportunity 读的就是真实逐字稿，那是这个项目里唯一一处真用户语料，而它现在只用来找商机。
