四块的关系,用一句话说清:

  • 后台服务是门房。浏览器要什么都找它,它转身去问引擎或仓库。整个项目没有装任何第三方库,纯 Python 自带的东西(find 未发现 requirements.txt / package.json)。这在今天很少见,好处是「换台电脑就能跑」。
  • 状态流转引擎是规矩。它管的是「已付的押金能不能退回未付」这类问题 —— 15 台状态机,非法流转一律拒绝并说明理由。
  • 智能体是两个:一个替财务查退款为什么失败,一个替顾问答汉服工艺问题。它们共用同一段循环代码(agent/v1.py:73 的 run_case)。
  • 知识层是 10 份 Markdown。人在 md 里写,机器读的表由解析器生成,单向,不回写 —— 这样同一份知识不会存两遍、也就不会漂移。

拼接顺序:对的,但有一处白扔的钱

顺序是 system(固定)→ tools(固定)→ messages(变动)。这个顺序是对的 ——

稳定的东西在前,变动的在后,这正是能命中缓存的排法。

但实测 118 次调用,缓存命中 = 0。

输入 377,898 token   输出 34,359 token   缓存命中 0
输入是输出的 11.0 倍

输入是输出的 11 倍,说明绝大部分钱花在「每轮把同样的东西重发一遍」上:

每次调用重发的固定部分:
  系统提示词  653 token
  工具说明书  941 token          ← 工艺顾问的 5 个工具
  ─────────────────
  ≈ 1,600 token × 118 次 = 约 19 万 token 是重复的

第 3 版实测:量出来了,答案是不能省

第 2 版这里写的是「不能承诺一定省,要先量」。装上记录仪之后做了对照实验:

同一个问题各问两遍,一组关缓存、一组开。

组      轮    输入   缓存命中  缓存写入      成本
A 关    1    3795       0        0     $0.00418
A 关    2    4068       0        0     $0.00443
B 开    1    3795       0        0     $0.00417
B 开    2    4065       0        0     $0.00439

开与不开完全一样,而且「缓存写入」也是 0 —— 说明缓存根本没被创建,

不是创建了没命中。没有报错,是静默失效。

原因查到了,是模型的最小可缓存前缀门槛:

模型最小可缓存前缀
Claude Opus 5 / Fable 5512
Opus 4.8 / Sonnet 5 / Sonnet 4.61,024
Opus 4.72,048
Haiku 4.5(你在用的)4,096

你的可缓存前缀(工具说明书 + 系统提示词)约 1,600 token,

远低于 Haiku 4.5 的 4,096 → 静默不缓存,和实测完全对上。

这条门槛不是随代际单调下降的 —— 最新的 Opus 5 是 512,而 Haiku 4.5 是 4096。

也就是说:同一段提示词,在 Opus 5 上会缓存,在 Haiku 4.5 上不会。

结论与行动:

  • 现在用 Haiku(因为它是独立额度池),缓存这条路走不通,不必再折腾
  • 缓存开关已留在代码里(PROMPT_CACHE=1),等哪天换到 Opus 5 就自动生效
  • 真要在 Haiku 上省钱,方向不是缓存,是减少每轮重发的量(比如工具说明书写短些)
出处:Anthropic 提示词缓存文档(最小前缀门槛表、"Shorter prefixes silently won't cache
even with a marker — no error, just cache_creation_input_tokens: 0")
https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching

结构化输出:你已经在正确的那一级

退款定因用 submit_finding 这个工具的 schema 强制结构(agent/v1.py:54),

而不是在提示词里求它「请输出 JSON」。

这两者差一个等级:求它输出 JSON,它有时会多写一句「好的,以下是 JSON:」把解析搞崩;

用工具 schema,格式是 API 层面保证的。你走的是对的那条。

工艺顾问是纯文本输出 —— 这是对的,因为它的产出是给人读的话术。

四、检索与评测现状

a. 检索:你有知识库,但没有用 RAG,而这是对的

「RAG」是把文档切块、转成向量、按语义相似度捞回来的做法。你一点没用 ——

api.py 里全是 SQL 精确查询和关键词 in 匹配。

判断:现在不该上 RAG。 理由三条:

  1. 你的知识是结构化的(60 个条目、每条有分类和来源等级、外加一张相容矩阵), 而 RAG 擅长的是非结构化长文本
  2. 精确查询可解释:kb_combo(妆花, 云锦) → 可,依据是哪一行清清楚楚。 向量检索给的是「最像的三段文字」,说不清为什么
  3. 便宜、快、不会「捞回相近但不对」的东西

什么时候该重新考虑:条目上千条,或者要检索的变成自由文本

(比如把工艺师傅历年的经验笔记也纳进来)。到那天再上,现在上是过度设计。

b. 评测:三套,是我见过的同阶段项目里做得最认真的

评测集题数成绩有没有负向题
退款定因(正向)2018/20 = 90%—
退款定因(负向)85/8 = 63%✅
工艺顾问2020/20✅ 6 题(30%)

做对的三件事:

  1. 有负向题。绝大多数项目只测「该做的做对了没」,不测「不该做的有没有不做」。 你的负向题抓到了真问题:一张证据残缺的单子,模型给了置信度高并编出完整因果链
  2. 判分器有自测。chat 那套重判后 20/20,而三条翻转全在往通过方向 —— 这是过拟合的典型特征。你另建了 chat_eval_judgetest.py,喂 18 条人造答案验两个方向, 这才是 20/20 可信的依据,不是分数本身
  3. 判据落在客观事实上。相容类问题比对「结论和工具返回的 verdict 一不一致」, 而不是「答案里有没有某个词」

三个缺口:

缺口说明
样本量 n=1每题只跑一次。模型有随机性 —— 实测中 N7 那题两次跑出了不同结果。现在的分数说明得了数量级,说明不了稳定性
没分「能力集」和「回归集」应该分两套:能力集难、暴露不足(理想分 60);回归集发版必过(理想分 90+)。现在混在一起
相容矩阵完成度 6%273 格填了 16 格。「查不到」在真实使用中会非常频繁,而那正是最容易诱发编造的场景

1. 把相容矩阵从「查得到」变成「拦得住」(现在最紧急)

这是我们刚才聊到一半的那件事。现在矩阵只有顾问主动问 chat 时才会被读到,

学到的东西:Tool 和 Hook 的分界线 —— 同一份知识,挂在 Tool 上是「查得到」,

挂在 Hook 上才是「拦得住」;分界的判据不是技术,是这件事会不会有人主动去问。

出处:Anthropic《Building Effective Agents》
https://www.anthropic.com/engineering/building-effective-agents

附:这个项目做得好的地方(别只看问题)

  1. 验证环强得反常。7 项自动检查、3 套评测、判分器自测 —— 而且每次修完检查器, 你都会塞一个真的坏东西进去复验它还会不会失败。这个习惯比任何一项检查本身都值钱。
  2. 知识层单向生成。md 是唯一源头,表由解析器生成。多数人会两边各存一份,然后半年后发现对不上。
  3. 来源分层。60 条知识每条都标了 public / scale / demo。 「哪些能对客户说」这件事被做成了可查询的字段,而不是靠人记。
  4. 零依赖。整个项目只用 Python 标准库,换台电脑就能跑。
  5. 提交的是绿的状态。两次首提交之前都先跑了全套检查确认通过 —— 这意味着版本历史里的每一个点都是「能跑的」,而不是「当时刚好写到这」。
