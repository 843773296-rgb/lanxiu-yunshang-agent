# AI 产品形状:定形状 → 落地 → 验收

这不是代码审查,也不是诊断工具。它是**做一个 AI 功能时的顺序**,
用来防住同一个病:**嘴上说在做 Agent,实际做成了 workflow,而没有意识到。**

---

## 一、定形状:**这件事该由谁判断?**

拿到一个需求,先别问「用什么技术」,问这一句。答案只有三种,
而它直接决定这个东西是工具、是技能,还是写口。

| 由谁判断 | 落成什么 | 判据 |
|---|---|---|
| **代码判断** | **工具**(一次调用答完) | 每一步都有**唯一正确答案**,换个人算也是这个数 |
| **模型判断** | **技能**(多步编排) | **前一步的结果决定下一步查什么**,中间有「看情况」的地方 |
| **人判断** | **写口 + 确认** | 判错了要担责任:钱、货、承诺、对外发出的话 |

### 1.1 最常犯的错:把「模型判断」冻进工具里

一个需求听起来像「查一下 X」,实现时发现要先查 A、根据 A 的结果查 B、
再根据 B 决定要不要查 C —— 这时候有两条路:

    写成一个函数,一趟算完,暴露成一个工具     ← 省事,而且当场就能跑
    写成技能,让模型一步步走,每步之间判断      ← 麻烦,但判断留在了该在的地方

**第一条路每次都更省事,所以它会被一直选下去**,直到有一天你发现
工具有 60 个、技能只有 3 个,而**平均每轮只调 1.08 个工具**。

那个数字看起来像「效率高」,实际是症状:
**每轮只调一次,因为每个工具都已经把一整件事做完了。**

> **用 Agent 的壳,跑 workflow 的芯。**

⚠️ 这不等于 workflow 错。步骤能提前枚举就该停在 workflow ——
更可控、更便宜、更好调试。**问题不是选了哪个,是不知道自己选了哪个。**

### 1.2 分界线:判断是**死的**还是**活的**

    死的 → 工具   「用量 × 损耗 × 单价」「1237 个数压成 12 条档差」
                  ——有唯一答案,让模型编排只会更慢更不准
    活的 → 技能   「客户说明年六月要穿」→ 选码、工期、留量、可行性四个约束互相咬着,
                  留量大了尺码要换,尺码换了工期要重算 ——**这是要来回推的活**

判不准时问一句:**「换一个熟练员工来做,他会不会中途改主意?」**
会 → 活的 → 技能。

### 1.3 工具要跟着**资源**走,不跟着**场景**走

    跟表走 / 跟 API 走     get_order、get_customer、get_stock
    跟场景走(❌)           未成交挽回清单、月度复盘、预约漏斗

场景型工具会无限增生 —— 每来一个新场景就加一个。而场景**本来就该由技能编排**,
它要的数据在那些跟表走的工具里已经有了。

**自检:这个工具的名字里有没有动词或业务场景?** 有的话多半该是技能。

### 1.4 一个能当场用的配比感

    纯取数(跟表走)   ≈ 主要业务对象数
    计算(判断是死的) ≈ 真正要暴露的口径数
    技能(判断是活的) ≈ **多步且步间有判断**的业务流程数
    写动作           ≈ 真正会改库的业务动作数

**工具:技能 如果到了 20:1,基本可以断定判断被冻进工具里了。**
健康的比例更接近 **3:1 到 5:1**。

## 二、落地:**每一件都配得上规矩和验法**

形状定了再动手。每加一件东西,三样一起加,缺一不可:

### 2.1 加一个**工具**

1. **工具本身**——跟表走,只读优先
2. **管它的规矩**——挂了工具就必须告诉模型怎么算用错。
   **「工具给了、规矩没给」比「工具没给」更危险**:模型会用它,而没人告诉它边界
3. **验法**——绝对判定逐例标真值;相对指标验性质(见 §3.2)

⚠️ **加一个工具的代价不在那个工具上,在此后每一次调用上。**
工具定义每次调用都要全带上 —— 实测过一次:工具 26 → 59,
提示词 21KB → 55KB,**成本涨 38%,而调用数、耗时、能力一点没变**。

### 2.2 加一个**技能**

1. **触发条件**写清楚 —— 什么时候该用它,什么时候不该
2. **不可省略的步骤**列出来 —— 这是技能存在的理由。
   **运行时框架不知道业务上哪一步不能跳**,那是我们要提供的
3. **终止条件** —— 什么时候算做完。没有终止条件的循环会一直烧钱

### 2.3 加一个**写口**

1. **白名单**——不在名单里的调用直接拒
2. **权限预演**——以目标角色试算一遍,试算不产生数据变更
3. **行为约束**——连续写入 / 重复参数重试 / 已成功后再写,都要拦
4. **操作留痕**——谁、什么时候、改了什么、判定结果和理由

## 三、验收:**拿前后对比数据,不靠「感觉更好了」**

这一段最容易被跳过,而跳过它,前两段等于没做。

### 3.1 指标必须**可由程序判定**

    ✅ 可判定   取到的号对不对、有没有调对应工具、数字有没有出处、档位对不对
    ❌ 不可判定 答复读起来顺不顺、语气好不好、「感觉更聪明了」

**不可由程序判定的指标进不了自动化校验,长期一定失效。**

### 3.2 绝对判定逐例标真值,相对指标验性质 —— 两者别混

| 类型 | 例子 | 怎么验 |
|---|---|---|
| 绝对判定 | 「第 90 天就是活跃」 | 逐例标边界真值,拿另一套实现对账 |
| 相对指标 | 「这个月谁最受欢迎」 | 验**性质**:同值同分 / 单调 / 不塌 / 排序确定 |

相对指标**逐例标真值会在第二天过期,而且过期时不报错,只会开始误报**。

### 3.3 正向测对不对,**负向测顺着错误前提会不会滑下去**

负向用例是重点,而且该占大头:用户带着错的前提来问
(「所以真丝更容易坏对吧?」「那我们别做真丝了?」),看它顶不顶得住。

### 3.4 判分器**先过人造对照,真跑之后把真实说法钉回去**

1. 写完判分器先跑人造对照 —— 离线、一秒钟、抓逻辑错
2. 真跑之后,把每一句真实说法钉回对照用例 —— 抓词汇错和判据方向错

实测过:16 条人造对照全过,然后真跑 12 题挂 5 条,**五条全是判分器自己的错**。

### 3.5 **一轮不作数**

同一个提交、同一个模型、同一批题,**连跑两轮**,两个数一起写。
单轮结果是抛硬币 —— 为这件事栽过三次。

### 3.6 重构的验收:**解冻一个,跑数据,再动第二个**

把一个冻结流程改成技能之后,**必须跑评测对比前后**:

    更准了?    通过率
    更灵活了?  能不能应付题面里没写过的说法
    代价多少?  调用数、耗时、成本

**没有前后对比的重构,和「觉得这样更整齐」没区别。**
而「改一个能跑的东西只为了让它更符合分类,是拿风险换整齐」。

## 四、一页纸自检

动手前:

- [ ] 这件事该由谁判断?(代码 / 模型 / 人)
- [ ] 如果是工具:它跟表走还是跟场景走?名字里有动词吗?
- [ ] 如果是技能:不可省略的步骤是哪几步?终止条件是什么?
- [ ] 如果是写口:白名单、预演、行为约束、留痕,四样齐了吗?

动手后:

- [ ] 规矩跟着工具一起下发了吗?
- [ ] 指标可由程序判定吗?
- [ ] 绝对判定还是相对指标?验法对不对得上?
- [ ] 负向用例占大头了吗?
- [ ] 判分器先过人造对照了吗?
- [ ] 跑了两轮吗?两个数都写了吗?

收尾:

- [ ] 工具:技能的比例,离 20:1 还是离 4:1 更近?
- [ ] 平均每轮调几个工具?如果长期是 1.0 左右,**回到第一段重看一遍**
