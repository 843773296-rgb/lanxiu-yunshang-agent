# 缓存 · 运行消费者清单（2026-10-04 实测）

> 缓存规格 §19 的**第一步**：「在迁入后的目标仓库核查最新运行入口，列出哪些入口
> 可写缓存参数、哪些只能读取用量；**只读证据不当执行测试**」。
>
> 这一份就是那个清单。**它是只读核查的结果，不是一次真实调用测试** ——
> 下面每一行的「证据」列写的是我查了什么，而不是我跑通了什么。

## 为什么先做这一份

规格 §9 的「运行接入模式」是一个五档的下拉：
**可控制 / 自动管理 / 仅观测 / 不支持 / 待确认**，并且明写
「**从适配器能力返回；用户不能自行改成「支持」**」。

而那五档要填得出来，前提是先知道每条入口到底能做什么。

> **一个「已开启」而实际没有消费者的开关，和一个真生效的开关，
> 在页面上长得一模一样** —— 而规格 §2 的实施约束第 3 条正是
> 「配置保存、发布绑定、运行时实际采用、供应商实际命中**分别记录**」。

而 2026-10-04 刚把缓存写入按 TTL 拆成两档（见下）。

## 两件实测出来的事，写下来免得以后当新发现

### ① V1 那个开关**只支持 5 分钟档**，所以「有效期」那一栏现在是「不支持」而不是「待确认」

`v1.py` 写进去的是 `{"type":"ephemeral"}`，**没有 `ttl` 字段**。
一手（`shared/prompt-caching.md`）：`cache_control` 支持 `ttl:"1h"`，
而不写就是默认的 5 分钟。

所以规格 §9 的「有效期」配置项在 V1 这条入口上，当前只能给一个值。
把它做成「供应商默认 / 支持的期限」下拉时，**那个下拉在 V1 上只有一项** ——
而规格自己要求「**从能力快照派生，不提供供应商不支持的任意分钟输入框**」。

### ② V1 那个开关有一个**静默失效**的条件

```python
if (cache if cache is not None else os.environ.get("PROMPT_CACHE")=="1") \
   and isinstance(body.get("system"), str):
```

第二个条件是 `system` 必须是**字符串**。如果哪天有人把 `system` 改成块列表
（Claude API 完全支持那种形状，而且做多个缓存断点时**必须**用那种形状），
这个开关开着也**什么都不做，而且不报错**。

实测现在不会踩到：全仓唯一把 `system` 变成列表的地方，就是这个分支自己（`v1.py:124`）。
但它正是规格 §B-2 那条教训说的形状：

> **每个配置控件都要有实际消费者和可以观察的生效证据。**

⚠️ **这一条目前只是隐患，不是 bug。** 真要修的时机是「给策略加第二个缓存断点」
那一天 —— 到那天 `system` 就得是列表，而这个条件会让整个策略静默失效。
修法不是删掉那个 `isinstance`（那会让列表形状被当字符串拼坏），
而是**两种形状各走一条路，并且都要能在用量里看到写入**。

## 2026-10-04 同一轮做掉的：缓存写入按 TTL 分档

这件事不在规格 §19 第一步里，但它是**第一步的直接产物** ——
清查「能读哪些用量」时发现账是错的（潜在）：

| | |
|---|---|
| 真相 | `cache_creation_input_tokens` 是 **5 分钟 + 1 小时两档的合计**（一手：`shared/prompt-caching.md`） |
| 单价 | 5 分钟 **1.25×**、1 小时 **2×** 普通输入价（同一份一手） |
| 原来 | 价目表只有一个 `cache_creation_input_tokens: 1.25`（5 分钟档的价） |
| 后果 | 一旦出现 1 小时写入，它的 token 按 1.25 计价 —— **那一档上少算 37.5%** |
| 已发生吗 | **没有。** 记录仪 6093 条调用里 1 小时档写入 **0 条**，代码里也没人设 `ttl:"1h"` |
| 为什么现在修 | **规格 §9 要给编辑者一个「有效期」下拉** —— 那份规格本身会造出触发这个错账的条件。先修账，再开那个开关 |

⚠️ 而原有那道「认不出的档要报出来」的闸**拦不住它**：
嵌套的 `cache_creation` 确实会被报成「认不出」，**可钱早就按合计算完了**。

> **一道装在错位置的闸，和一道没装的闸，在它响的时候长得一样。**

改法和判据：`services/api/app/knowledge/usage.py` 的 `归一用量` 按
`usage.cache_creation` 拆成 `ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`
两档分别计价；**分档之和 ≠ 合计，或者出现没见过的 TTL 键 → 当场报出来，不挑一个用**
（挑合计会漏掉新档的单价，挑分档会少算那部分 token）。
`tests/orchestration/test_usage.py` 第 ⑩ 组 9 条钉着它，包括
「全走 5 分钟档时和旧口径**一字不差**」——所以这次改动不会让已有的账变样。

## 这一份没回答什么

- **没有任何一条做过真实调用测试。** 上面全是源码核查。
  规格 §C.1 把「真实供应商」单列一层，需要有额度的测试者跑。
- **没验「V1 那个开关真的让供应商命中了」。** 要验它得看回执里
  `cache_read_input_tokens > 0`，而那要真发两次请求。
- **没查 DeepSeek 那条路的缓存能力。** 价目表里它只有
  `cache_read_input_tokens`，没有写入档 —— 那可能是「它不收写入费」，
  也可能是「我们没登记」。**这两件事在价目表上长得一样**，待核。
