# ⚠️ 更正(2026-10-03 当天晚些)——**下面那条「38」是错的,真实是 148**

第二层评测(真跑模型,两轮 × 两臂 × 24 题)跑完之后,式子里**少的那一项量出来了**。
下面第一节的推导**只算了「省下的工具定义 vs 路由器一次的钱」**,而漏了:

> **模型拿到一个不太合适的工具之后干的事。**

实测(两臂各 24 条,同提示词同池子):

| | 基线(77 个工具) | 筛选(1.4 个) | 差价 |
|---|---|---|---|
| 输出 token | 1527 | 1731 | **$+0.00102**(输出 $5/百万) |
| **读缓存 token** | 320767 | 345450 | **$+0.00247**(缓存读 $0.1/百万) |
| | | **合计** | **$+0.00349/条** |

而**路由器那一次调用只要 $0.00089** ——
> **「反复试」的代价是路由器那一次调用的 4 倍。**

我一直把路由器那一次调用当成「筛选的代价」。**真正的代价不在那儿。**

### 完整的式子

```
净 > 0  ⟺  省下的工具定义  >  路由器一次的钱 + **反复试的代价**
        ⟺  (N − 1.3) × 297.6 × 1e-7  >  0.00089 + 0.00349
        ⟺  N > 148.3
```

### 代回去:**没有任何角色能过线**

| 角色 | 工具数 | 线 148 |
|---|---|---|
| `all` | 77 | ❌ |
| `task` | 61 | ❌ |
| `kb` | 43 | ❌ |
| `pattern` / `workshop` / `finance` | 9 / 7 / 5 | ❌ |

**工具面总共只有 81 个,而线是 148。** 也就是说:
> **按现在量到的数,这个项目的任何角色都不该开工具筛选。**

### 「读缓存多 2.5 万 token」为什么会发生

工具返回的内容进了上下文,而**下一次调用要把整个上下文再读一遍** ——
重复调 7 次 `kb_read`(实测 T07),就是 7 次全量重读。
所以**重复调工具的代价不是「多调一次」,是「多读整个上下文一次」**。

### ⚠️ 这条更正自己的限定

- **11/48 题在两轮之间翻面**(轨迹类 5 题)—— 所以这些差值本身带着抖动
- 只量了 24 题、一个模型(haiku-4-5)、一个角色(`all`)
- **没量「如果筛选器选得更准会怎样」** —— 这些数说的是
  「**路由器现在这个准度下**筛选不划算」,不是「筛选这件事不划算」

## 一、线:**工具数 ≥ 38 才值得开**

**路由器那一次调用是固定成本,而筛选的收益随工具数缩** ——
所以小角色必亏,这不是调参能救的。

```
净收益 > 0
  ⟺ (N − 均留) × 每个工具平均token × 缓存读单价  >  路由器一次的钱
  ⟺ (N − 1.3) × 298 × 1e-7                    >  0.00109
  ⟺ N > 37.9
```

| 这四个数从哪来 | |
|---|---|
| `0.00109` | 路由器单条成本,**实测**(33 道留出题 × 带提示词缓存,haiku-4-5) |
| `1.3` | 路由器平均选几个工具,**实测** |
| `298` | 81 个工具定义的平均 token(说明 + 入参 schema,中文按 1 字 1 token 估) |
| `1e-7` | haiku-4-5 的**缓存读**单价 $0.1/百万 —— 从 `agent/v1.py::PRICE` 取,**没自己填** |

|---|---|---|---|---|---|

## 三、⚠️ 这条线**不许写死**

它随三个数漂:**路由器单价、每个工具平均 token、走不走缓存**。

> **写死 38 的那天模型降价它就错了,而错的时候不报错** ——
> 一个用过期的线算出来的「这个角色不该开筛选」,
> 和一个算对了的,在日志上长得一模一样。

所以:**现算**,并且把那三个数**一起记进日志** ——
不然事后看到「没开筛选」查不出是因为哪个数。

### 缓存那一条尤其要紧

省下来的那部分按**缓存读**单价算。**不走缓存的话单价高 10 倍**
(入 $1.0/百万 vs 缓存读 $0.1/百万),那时候线会降到 **≈ 5**,
也就是**几乎所有角色都该开**。

所以这条线的真实含义是:
> **在缓存命中率高的系统里,筛选只对大角色划得来;
> 而缓存一旦失效,筛选立刻对所有角色都划得来。**

(这个项目实测缓存命中占输入的 **97.9%** —— 所以用缓存读那一档算是对的。)

## 四、兜底组取交集之后剩几个(队友那条规矩的直接后果)

队友定的规矩:**筛选结果和 `_ROLE_TOOLS[kind]` 取交集,只许收窄不许放宽** ——
角色的工具集是**权限边界**(财务不给量体/版型),而规格明写「筛选得分高**不**授予权限」。
那 20 个只读兜底组同理要取交集。

| 角色 | 兜底组交集 | |
|---|---|---|
| `all` | 20 | |
| `kb` | 13 | |
| `task` | 11 | |
| `workshop` | 6 | |
| `pattern` | **2** | ⚠️ |
| `finance` | **1** | ⚠️ **退回它等于退回一个空壳** |

**好消息是这两个角色正好也不过线** —— 不开筛选就用不到兜底组,两件事互相对上了。

但要配一道闸:**过线要开筛选、而兜底交集 < 5 个 → 当场报**。
免得哪天线动了、某个小角色过线了,而它的兜底是个空壳。
> 一个退回到空壳兜底组的筛选,和一个正常退回的,在「退回了」这个事实上长得一样。

## 五、三条局限,不许省

- **「筛到 1.3 个」是拿全局平均估的** —— 小角色上路由器未必还能筛到 1.3,
  工具越少越难再砍。所以小角色那几行的「省」是**高估**,实际净亏更多
- **只算了工具定义省的**,没算对应那条规矩(旋钮收窄不动提示词)——
  所以大角色那几行的「省」是**下限**,实际更多
- **没算延迟**。路由器延迟中位 1.6s,而规格的筛选超时预算是 3000ms。
  小角色上那 1.6s 换来几乎零收益,**那笔时间比钱更明显**

## 六、两道闸一前一后(和队友分工)

| | 挡什么 | 怎么挡 |
|---|---|---|
| **准入线**(这份文档) | 算得出来的 —— 工具数不够,连路由器都别调 | `_tools_for` 决定走哪条路之前现算 |
| **空集退回计数**(队友提的) | 算不出来的 —— 某个角色的问法特别散,路由器老是选空 | 运行时统计比例,超标报警 |

> 线挡掉算得出来的,计数器挡掉算不出来的。**两个都要。**
