## 一、先看现状数据(**不是推断,是量出来的**)

| 哪里 | 工具数 | 说明 |
|---|---|---|
| 后台的工具目录 | **2 个** | 搜索(只读)+ 写报告(不可逆),说明平均 33 字 |
| **澜绣 V3 实际在跑** | **59 个** | 从 26 个涨上来的 —— 而那次涨让**单条成本涨了 38%** |

而那 59 个在 **MCP 服务器**里(`mcp/kb_server.py` / `task_server.py` /
`shop_server.py`),**不在后台的工具目录里**。

### ⚠️ 这两个数改变了问题本身

> **一个在 2 个工具上做的筛选器,它的召回率永远是 100%** —— 而那个数字毫无意义。

规格 §4.1 自己也写着:「**不因示例有多个工具就强行新增搜索集群**」。

所以真正要定的不是「用哪种检索算法」,而是:

> **在哪一侧做,以及后台的工具目录要不要先装上那 59 个。**

(这和 10-02 做完的那三条待办是同一个形状 ——
「后台管着自己造的演示数据」,只是这次落在**工具**上。)

---

## 二、三个方案

### 方案 A:先把那 59 个工具装进后台目录,再做检索

| | |
|---|---|
| **用户感觉得到什么** | 后台的工具目录里第一次出现**真工具**;筛选的分数第一次有意义 |
| **锁死了什么** | 工具目录成了 MCP 工具的**第二份登记** —— 两边迟早漂,要一条同步判据(和 10-02 那三条同形) |
| **代价** | MCP 工具的定义要能导出成工具版本(名字/说明/入参 schema);而 MCP 那三个服务器是裸手写 JSON-RPC,没有统一导出口 |
| **业界叫什么** | 这是 **MCP 的工具发现(tools/list)+ 导入审核**,规格 §5.2 和 §13.1 写的正是它 |

### 方案 B:检索只在后台目录上做,不碰那 59 个

| | |
|---|---|
| **用户感觉得到什么** | 后台能配能跑能看证据,**而筛选的数字没有参考价值**(2 个工具) |
| **锁死了什么** | 它会被当成「筛选做完了」—— 而真正要筛选的那 59 个没被管到 |
| **代价** | 做完之后仍然要做方案 A;**而那时已经有一套在 2 个工具上调过的参数** |
| **诚实说** | 这是**演示级实现**,不是能回答「筛选有没有用」的实现 |

### 方案 C:先做评测口径,**不做检索**

| | |
|---|---|
| **用户感觉得到什么** | 能回答「不筛选 vs 筛选,哪个答得对、各花多少」—— 而暂时没有筛选器 |
| **锁死了什么** | 没有。它是方案 A/B 的**前置**:没有口径,做出来的筛选器好不好说不清 |
| **代价** | 要一套同题评测(规格 A-8 已经写了判定口径);**而它不产出任何界面** |
| **业界叫什么** | 这是 **先定度量再优化**。你那个项目一直在这么做(三代对比表、「判对」那一栏写两个数) |

---

## 三、我推荐 **C → A → B 的顺序**,而不是直接做 B

### 为什么先做 C(评测口径)

你那个项目反复栽在「**先做了再问它有没有用**」上 ——
而现成的教训就在 CLAUDE.md 里:

> 「另一条线报『热词让行业词召回从 40% 涨到 73%』,**那 33 个百分点是假的**」
> 「**不符合预期的数会被查,符合预期的数会被信。**」

筛选器正是最容易出这种假收益的地方:**少挂几个工具,成本一定降** ——
那个数字一定好看,而「答得对不对」要另外量。

### 为什么 A 在 B 前面

> **一个在 2 个工具上调出来的参数,换到 59 个工具上重新调一遍,
> 和从头调没有区别** —— 而中间那段时间它会被当成「已经调好了」。

### 为什么不直接做 A

A 要先解决「MCP 工具怎么导出成工具版本」——
而那三个服务器是裸手写的,没有统一导出口。那是一块独立的活。

---

## 四、参数:**现在不定**

规格 §14.3 给了五个初值(候选 5 / 新增额度 4000 / 活动额度 12000 /
补搜 2 次 / 超时 3000ms),而它们是**设计初值,不是实测出来的** ——
规格自己也这么写。

> 在 2 个工具上调这五个数**没有意义**:候选上限 5 永远碰不到。

所以:**等工具目录装上真工具、评测口径立起来之后再调**,
而且调的时候要按 A-8 的口径同时看「答得对」和「花了多少」。

---

## 五、怎么验证(**先写进卡里,不等做完再想**)

| 要验什么 | 怎么验 |
|---|---|
| 召回对不对 | **逐例真值**:挑 20 个真实任务,人工标「这个任务该用哪几个工具」 |
| 筛选有没有用 | **同题对比**:同一套题,全量挂 vs 筛选,比「答对数」和「每条成本」 |
| 不是靠少挂工具省钱 | **两个数一起报** —— 成本降了而答对数掉了,那不叫改进 |
| 边界 | 候选为空、预算放不下必需工具、补搜耗尽 —— 各一条反例 |

⚠️ **判定口径用 A-8 那一套**(成功要全部必要条件 + 没有禁止行为;
支持多条合法路径;比例同时报分子分母)。

## 八之一、拍板之后量出来的三件,改了这张卡的前提

### ① 「59 个」这个数已经过期 —— 现在是 **77**

```
工具面总数            81
all      (默认入口)   77     ← 这才是「全量挂」的基线
task                  61
kb                    43
pattern  9 · workshop 7 · finance 5
```

卡的第一节写「澜绣 V3 实际在跑 59 个」,那是 09-16 的数。**两周涨了 18 个。**
而 CLAUDE.md 已经记着「从 26 涨到 59」让单条成本涨了 38% —— 这条曲线还在涨。

> **一个写在文档里的数,和一个现在量出来的数,在读的时候长得一模一样。**

### ② 澜绣**已经有一套工具筛选在跑** —— 就是「按角色发工具」

`agentsite/sdk.py` 的 `_ROLE_TOOLS` 把 77 个工具按六个角色切开,硬编码的。
**那正是规格 §4.2 的「固定工具组」模式。**

所以后台这块不是从无到有,是**把硬编码的那套搬进可配置的后台**。
而对评测的影响是**要加一组**:

| 组 | 工具面 | 是什么 |
|---|---|---|
| 全量 | 77 | 不筛选 |
| **按角色** | **5–61** | **现状。硬编码的固定工具组** |
| 动态筛选 | ? | 待做 |

> **少了中间那一组,评测会把「按角色分组本来就省下的钱」算到动态筛选头上。**
> 那就是 CLAUDE.md 里记的那次 —— 「召回从 40% 涨到 73%,那 33 个百分点是假的」的同一个形状。

### ③ 「同题跑不同工具面」的机制**已经有了** —— 旋钮方案

`agent/knobs.py` 的 `工具` 旋钮(类型「工具子集」)。而且它守着**只许收窄不许放宽**:
白名单外的工具当场抛。三组都是 77 的子集,正好。

⚠️ **但它只收窄工具定义,不收窄提示词。** 收窄之后,提示词里仍然带着那些
不在场的工具的规矩。所以:

> **筛选省的钱分两份 —— 工具定义,和对应的那条规矩。旋钮收窄只省前一份。**

**两个数要分开报**,否则「筛选能省多少」会被低估(漏了提示词那半),
而**低估和高估一样坏** —— 它会让人以为筛选不值得做。

## 八之二、现有 `tool_eval.py` 为什么不能直接当口径用

它已经在考「工具变多之后会不会用错」,22 题,三轴(轨迹 / 内容 / 体检)。
但有三条结构性的拦路:

| | 现状 | 为什么测不出筛选 |
|---|---|---|
| 角色 | **22 题全是 `kb` 一个角色** | 77 个工具都在场时最容易选错的是**跨角色**(问尺码去查产能),而一题都没有 |
| 必需工具数 | 平均 **1.2 个** | 候选上限 5 永远碰不到边界 |
| 禁调真值 | **一条都没有** | 而它自己的文件头写着「多调了不该调的,每一次都是钱」 |

还有一条口径上的分水岭:`tool_eval.judge` 里 `need` 判的是
`any(n in names for n in need)` —— **「至少调对一个」**,
而注释写的是「必须出现」。那个语义对它那 22 题是对的(T07 三个工具择一),
**但测筛选要的是「全部必需都在」**(A-8 口径:成功要全部必要条件)。

> 两种语义都合理,**而它们在判分器里长得一模一样**。所以新开一份,不改那一份。
