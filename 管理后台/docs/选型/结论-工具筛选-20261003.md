## 二、唯一硬的那个数:**成本的机制**

答对数分辨不出来,但**成本的机制是清楚的**(两版都指向同一件事):

| | 基线(77 个工具) | 筛选(1.4 个) |
|---|---|---|
| 平均来回轮数 | 1.25 | 1.33(**+0.08,没差**) |
| 平均调几个工具 | 1.92 | **2.21** |
| **重复调同一工具** | **8 次** | **15 次** |

> **工具少了,模型不是绕更多圈,而是在同一个工具上反复换参数试** ——
> 因为它手里没有更合适的那一个。

T07 最刺眼:基线 `kb_lookup`×3 + `kb_read`×2 → 筛选 `kb_lookup`×4 + **`kb_read`×7**。

**而代价的大头不是输出,是读缓存**:工具返回的内容进了上下文,
**下一次调用要把整个上下文再读一遍** —— 重复调 7 次就是 7 次全量重读。

> **重复调工具的代价不是「多调一次」,是「多读整个上下文一次」。**

这条机制**与「开不开筛选」这个决定无关,而且它一定成立** —— 已记进 PRD 附录 B-101。

## 四、什么时候该重新问这个问题(触发条件,不是日程)

准入线是**现算的**(`agent/tool_select.py`,23 条自测 + 咬合过),所以它会在这三件事发生时**自己翻过来**:

1. **缓存命中率掉下来** —— 省的部分按**缓存读**单价算。不走缓存单价高 10 倍,
   线从 148 降到 ≈ 5,**几乎所有角色都该开**。
   (本项目实测缓存命中占输入 **97.9%**,所以现在按缓存读那一档算是对的。)
2. **工具数涨上去** —— 线是 148,而现在工具面只有 81 个。**工具再翻一倍就过线。**
   而这个项目的工具数:26 → 59 → 81,**两周涨 18 个**。
3. **路由器准度提上去** —— 现在的数说的是
   「**路由器现在这个准度下**筛选不划算」,不是「筛选这件事不划算」。
   而提准度的路不是换算法:**是给工具加业务话别名**(见下)。

⚠️ **不许把 148 写死。** 它随三个数漂(路由器单价、每个工具平均 token、走不走缓存),
> **写死的那天模型降价它就错了,而错的时候不报错。**

## 五、这条线真正的瓶颈,不在筛选上

两个独立留出集在**同一个地方**失败,而那才是根:

```
藏青 S 码那件马面裙现在还能发几件?   → 需要「查现货」,和问法**一个共同片段都没有**
灰缬能做在浅色棉麻上吗?              → 需要「相容矩阵」,没有
我今天有什么活?                     → 没有
今天该我核什么?                     → 没有
PT01 这个版型的裁片用料占比是多少?    → 没有
```

> **用户问的是业务,工具说明写的是系统。**
> 所以**关键词检索在这里真正检索的是「用户恰好用了说明里的词吗」** —— 而用户不读说明。

而别名表这条路**从日志挖已经到顶了**:47/81 个工具有别名,
而 `kb_*` 那一族(工艺/面料/工期/BOM/相容矩阵)**一条都没有** ——
不是顾问不问,是那条线的评测不记轨迹。

**下一步真正该做的是这件,不是换检索算法。**
这是三大鸿沟里的**第一条「理解鸿沟」** —— 不知道用户真会怎么问。
最小一步:`call_opportunity` 读的是**真实通话逐字稿**,
那是这个项目里唯一一处真用户语料,而它现在只用来找商机。
